# Spec: Welcome View & release surfaces

Status: ready-for-agent

## Problem Statement

ZotLit v2 replaces v1 in place (same plugin id), and the settings migration runs silently on first load. A v1 user who upgrades sees a plugin that loads and carries their folder paths — and nothing else. The migration guide on the docs site covers the three things they must still do by hand (confirm settings, refresh v1 notes into the Managed Region, migrate Eta templates), but the plugin never points them at it.

Worse, the upgrade detection leans on the migrated settings file. A v1 user who only ejected templates to customize them — and changed no other setting — never saved a settings file at all, so nothing marks them as an upgrader. They land in the fresh-install experience while their customized templates silently stop working: v2 looks in a different default folder for differently-named files, finds neither, and falls back to built-in defaults without a word.

Two adjacent gaps share the same trigger point:

- A brand-new user installs ZotLit into a fresh vault and lands in an empty workspace with no guidance on connecting Zotero, choosing folders, or creating their first Literature Note.
- An existing v2 user updates the plugin and has no in-app path to what changed; the docs site's changelog exists but nothing surfaces it.

## Solution

A single release service checks, once per launch after the workspace layout is ready, which of three situations applies, and surfaces the matching experience:

1. **Upgraded from v1** (Legacy Data was detected during settings load — or, when no settings file exists at all, ejected v1 templates were found in the vault): the **Welcome View** opens directly in the active leaf in its **upgraded** state, headed by the **Migration Prompt** — a prominent banner whose primary action opens the migration guide. The view auto-opens only on this detection launch. The migration-pending state it arms lives on afterwards as quiet in-context reminders — a "Finish migrating from v1" row atop the plugin's setting tab and a matching reminder on its Templates page — and a reopened Welcome View keeps showing the upgraded state while it lasts. The pending state resolves itself: while it is set, each launch re-probes the configured template folder, and once no ejected `zt-*.eta.md` files remain the reminders disappear; a "Mark as done" action on the setting row clears it by hand for users who keep the old files around.
2. **First install** (no settings on disk, no recorded version): the Welcome View opens directly in its **fresh** state — quick-start steps with live setup status and actions, documentation links, community links, and a quiet footer link to the migration guide for v1 veterans starting a new vault.
3. **Updated** (recorded version is lower than the current version): a durable notice announces the update; its action opens the **Release Note** — the per-version changelog page on the docs site — in a Web Viewer leaf when available, otherwise the system browser. External pages open only on user action.

In every situation, the setting tab opens with a headerless resources strip — "What's new in v{version}" opening the Release Note, "Browse docs", and "Get help" — so the changelog, documentation, and community stay reachable from a predictable place after each surface's moment passes.

## User Stories

1. As a v1 user upgrading in place, I want the plugin to open a migration landing page on first launch, so that I know settings migrated and what I still need to do by hand.
2. As a v1 upgrader, I want the Migration Prompt's primary action to open the migration guide, so that I can follow the refresh-notes and migrate-templates steps.
3. As a v1 upgrader, I want the migration reminder to persist in the plugin's settings after the first launch, so that a distracted first session cannot lose the pointer forever — without every startup being hijacked by a full-tab welcome screen.
4. As a v1 upgrader poking at template settings because my notes render wrong, I want the reminder repeated on the Templates settings page, so that the fix finds me where the breakage lives.
5. As a v1 upgrader who renamed my templates to the v2 pattern, I want the migration reminders to clear on their own, so that the upgrade experience ends when the work is actually done — not when I find a dismiss button.
6. As a v1 veteran starting a fresh vault, I want the fresh Welcome View to link the migration guide quietly, so that I can find v1-to-v2 guidance even though this vault has no Legacy Data.
7. As a new user, I want a welcome tab on first install, so that I can set up the plugin without reading external docs first.
8. As a new user, I want the welcome tab to show whether Zotero was auto-detected, so that I know if setup already succeeded.
9. As a new user whose Zotero was not found, I want a visible warning with a fix action, so that I can point the plugin at my data directory.
10. As a new user, I want quick-start steps with live action buttons (open settings, pick the Literature Note folder, search my library), so that I can complete setup from inside the view.
11. As a new user, I want documentation links grouped in the quick-start flow, so that deeper guides are one click away when I finish.
12. As a new user, I want community and news links present but quiet, so that I can find help and follow the project without them competing with setup.
13. As an existing v2 user updating the plugin, I want a persistent notice with a "see what's new" action, so that I learn about changes on my own schedule.
14. As an updating user, I want the Release Note to open inside Obsidian when the Web Viewer is available, so that I stay in my workspace.
15. As an updating user without the Web Viewer, I want the Release Note to open in my browser, so that the feature degrades gracefully.
16. As an updating user, I want nothing to open automatically, so that vault load is never hijacked by a web page.
17. As a user annoyed by update notices, I want a settings toggle that silences them, so that updates stay quiet.
18. As a pre-release user, I want alpha-to-alpha updates to surface Release Notes too, so that I see breaking changes during the alpha.
19. As a user who downgraded or reinstalled the same version, I want no update notice, so that only true upgrades announce themselves.
20. As a user with vault sync, I want seen-version and acknowledgment state to travel with the vault, so that a second device does not re-prompt for an upgrade I already handled.
21. As any user, I want commands that reopen the Welcome View and the Release Note, so that both surfaces stay reachable after their moment passes.
22. As a user browsing plugin settings, I want what's-new, docs, and get-help entry points at the top, so that the changelog, documentation, and community are one click away from a predictable place.
23. As a user with a corrupted settings file, I want the plugin to treat me as a fresh install for onboarding purposes, so that a malformed file produces guidance rather than nothing.
24. As a docs reader, I want each release to have a changelog entry at its per-version URL, so that the in-app Release Note action always lands on real content.
25. As a theme user, I want the Welcome View to render in Obsidian's native tokens in both color schemes, so that it looks at home under any theme and accent color.
26. As a v1 user who only ejected templates to customize them and never touched another setting, I want the upgrade prompt to still appear, so that I learn my customized templates need migrating instead of silently getting the built-in defaults.
27. As that same user, I want the plugin to keep pointing at my existing template folder after the upgrade, so that once I rename my templates they are found in place without my having to move files or reconfigure the folder.
28. As a v1 upgrader who keeps my old template files around after migrating, I want a "Mark as done" action on the settings reminder, so that I can end the migration state myself.
29. As a v1 upgrader reopening the Welcome View while migration is pending, I want it to show the upgraded state with the Migration Prompt, so that the banner mirrors the real pending state until it clears.

## Implementation Decisions

- One release service owns the launch check and all three branches. It runs after the workspace layout is ready, decides once, records state, and exits. First install and legacy upgrade are mutually exclusive with the update branch; the update branch fires only on a strict semver increase over the recorded version, so downgrades and reinstalls stay silent.
- **Branch decision is a pure function** — the service's orchestration (opening leaves, constructing notices, writing state) wraps a side-effect-free decision that maps (recorded previous version, current version, migration-pending flag, show-release-notes flag, settings hydration origin) to one of: open Welcome View upgraded, open Welcome View fresh, show update notice, do nothing — plus the state writes to perform. This is the primary test seam.
- **Legacy detection rides the existing settings classification.** Settings hydration already classifies disk data; the settings service additionally exposes the origin of the completed load (Legacy Data, absent/malformed, current) for same-launch consumption. The disk signal self-destructs when migration rewrites the file, so the release service reads the in-memory origin, never the disk.
- **State lives in synced plugin settings** under a `release.` namespace: the previously-seen version (string, absent until first check), whether update notices are enabled (boolean, default on, exposed as a settings toggle), and whether a Migration Prompt is pending acknowledgment (boolean). Sync semantics follow from the storage choice: acknowledging on one device clears everywhere; a version seen on one device suppresses re-prompts on others.
- The previously-seen version is recorded unconditionally at the end of every check (update branch = show-once). The migration-pending flag is set when Legacy Data (or ejected v1 templates on an absent settings load) is detected. It never re-opens the Welcome View on later launches — the upgraded auto-open happens exactly once, on the detection launch, because only the legacy and absent-with-templates origins take that branch. While the flag is set, each launch's check re-probes the configured template folder (the same in-memory scan detection uses, pointed at `template.folder` instead of the v1 default); when no `zt-*.eta.md` files remain, the check clears the flag — migration state mirrors the vault, and a v1 upgrader who never ejected templates resolves on their next launch. The existing acknowledge action survives as the manual clear, invoked from the setting-tab reminder's "Mark as done" control. The pure decision emits the auto-clear as a state write; the manual path stays a service method.
- Absent and malformed settings data both count as first install for branching purposes — except the absent case is first probed for ejected v1 templates (next bullet).
- **Templates-only v1 upgraders are detected from their ejected templates.** The Legacy Data signal lives in the settings file, but a v1 user who only ejected templates saved none, so the absent-settings branch additionally probes the vault before treating the launch as a first install. Only when the hydration origin is absent, the release service checks for the v1 default template folder `ZtTemplates` holding at least one `zt-*.eta.md` file (top-level, non-recursive, via the in-memory file index — no disk I/O). Presence feeds a `legacyTemplatesPresent` boolean into the pure decision alongside the origin. A new branch, ordered after the pending-flag check and before absent→fresh, fires when the origin is absent and templates are present: it takes the upgraded branch and arms the migration-pending flag exactly as Legacy Data does — writing a v2 settings file, after which the pending state carries on as the settings reminders (never startup re-opens). Scope is the absent origin only: a genuine v1 settings file has no version marker and already classifies as Legacy Data, so absent-settings is the sole no-settings upgrade path; malformed data stays on the first-install fallback.
- **The templates-only branch also reconstructs the template folder.** On that branch the release service sets `template.folder` to the v1 default `ZtTemplates` — reconstructing what the settings migration does when it carries the folder over from a real v1 file. Without it, v2 would keep looking in its own default `templates` folder and the user's renamed templates would still be invisible. The write lives in the service (it already owns the vault probe and the folder is a known constant), not in the pure decision output. Banner copy and migration guide are unchanged; the guide's rename-in-place steps then just work.
- **The Welcome View is a React ItemView** rendered under the plugin's scoped preflight root with prefixed Tailwind tokens, native Obsidian controls, and lucide icons. It opens in the active leaf. Its visual design is settled by prototype (see Further Notes): the Journey/Waypoint composition — wordmark + badge + tagline header; a vertical guided timeline of three quick-start steps (connect to Zotero with live connection status inside the step, choose the Literature Note folder, create the first Literature Note via library search) ending in a "Keep going" node holding the documentation chips; Community and News link rows below a hairline rule; green-ring done nodes.
- Connection status inside step one has three states — connected (profile path, library, item count), missing (warning with a locate-manually action), checking — driven by the existing Zotero profile/database services. The fresh-device launch surface pointing at this step (a durable notice when the database file is missing on this device) is owned by the multi-device-pref spec (`.scratch/multi-device-pref/SPEC.md`).
- **The Migration Prompt is the upgraded state's banner**, placed between the tagline and the timeline: accent-tinted panel, heading, one-line body, dominant call-to-action "Open migration guide". The banner has no dismiss control — it is informative, closing the tab is just closing the tab, and the pending lifecycle lives in the settings reminders. The body carries the banner alone — no leading icon or accent square. The fresh state carries the quiet footer link instead. Mode is chosen at open time: the release service's detection launch and every manual reopen pass upgraded while the pending flag is set, fresh otherwise.
- **Copy decisions** (all strings through Paraglide, house UI-text style):
  - The banner is action-first: it names the concrete manual work the upgrade requires and lets the "Open migration guide" CTA carry the detail. It leads on the single hard blocker for the typical v1 user — custom Eta templates stay inert until they are renamed to the v2 pattern and the JavaScript Templates gate is enabled — rather than reassuring about the automatic settings migration. The settings-migrated-automatically nod is dropped from the banner (settings need no user action, so they don't belong in a call to action); the guide, not the banner, enumerates the optional steps like refreshing v1 notes.
  - The migration guide matches this tone: it is restructured to foreground the manual work with a required-vs-optional summary up top — automatic (settings) · required to restore note generation (rename templates, `it.*`→`zt.*`, enable the gate) · optional (overwrite v1 notes for the managed region) — instead of framing the manual steps as leisurely "when you are ready."
  - The "Keep going" line explains only the documentation chips; the Community and News groups are self-explanatory and carry labels only.
  - The Sponsor chip renders the heart exactly once, as its icon.
- The Release Note opens the docs site's per-version changelog URL. Reuse-or-create a Web Viewer leaf when that core plugin is available; otherwise open the system browser. There is no bespoke iframe fallback view.
- Pre-release versions participate fully: an alpha bump triggers the update branch, and each release — including alphas — gets a changelog entry authored as part of the release process. The docs site's changelog collection and per-version routes already exist; entries are the missing piece, starting with the current v2 pre-release.
- Commands exist to reopen the Welcome View and the Release Note on demand; the settings tab gains the update-notice toggle.
- **The setting tab opens with a headerless resources strip** (the mx plugin's settings pattern): "What's new in v{version}" opening the Release Note through the existing Web-Viewer-or-browser logic, "Browse docs" opening the documentation site, and "Get help" opening the community page. Rows are plain native settings rows — name, description, one button — implemented on both the declarative (Obsidian ≥ 1.13) path and the compat path. The docs-site base URL collapses to a single shared constant (today it is duplicated between the welcome links module and the release constants).
- **The migration reminder is a conditional settings row** shown above the resources strip while migration is pending: it names the unfinished v1 migration, carries "Open migration guide" as its primary button, and a secondary "Mark as done" control wired to the existing acknowledge action. The Templates settings page repeats the same reminder. Both disappear reactively once the flag clears (auto or manual).

## Testing Decisions

- Good tests here exercise external behavior at the decision seam: given a recorded version, current version, flags, hydration origin, and `legacyTemplatesPresent`, the decision function returns the expected branch and state writes. Cover: first launch ever, legacy origin (pending set), pending relaunch with ejected templates still present (nothing opens, flag stays), pending relaunch with none left (flag auto-clears), acknowledged relaunch, strict version increase with notices on and off, equal version, downgrade, pre-release increase, malformed origin, absent origin with ejected templates (upgraded + pending set), absent origin without templates (fresh).
- The settings service's hydration-origin exposure is asserted where its classification behavior is already tested.
- Acknowledgment behavior tests through the service surface: acknowledging clears the pending flag. The auto-clear re-probe tests through the same surface: a pending launch whose configured template folder holds no ejected templates clears the flag; one where they remain leaves it set.
- The templates-only path's non-pure effects test through the release service surface: an absent settings load with a `ZtTemplates` folder holding a `zt-*.eta.md` file opens the upgraded view, arms the pending flag, and writes `template.folder = ZtTemplates`; an absent load without such a folder stays fresh and writes no folder.
- The Welcome View's rendering is not unit-tested; its states were settled visually by prototype and are verified against the running app via the Obsidian CLI loop. View actions dispatch to existing services, which own their own tests.
- Prior art: the settings package's pure classification/migration tests and its service tests over the mocked `obsidian` module.

## Out of Scope

- Settings data handling beyond what already shipped — the silent migration, its best-effort writes, and its key mapping are existing behavior this feature only reads from.
- Migrating the ejected template files themselves. Renaming to the v2 pattern, `it.*`→`zt.*`, and enabling the JavaScript Templates gate stay manual, documentation-driven steps; templates-only detection only surfaces the prompt and reconstructs the folder path.
- Detecting a templates-only upgrader behind a malformed settings file, or ejected templates in a non-default folder — both impossible without a settings file, which would itself classify as Legacy Data and take the existing upgrade branch.
- A bespoke in-app browser/iframe view for Release Notes (the mx plugin's fallback). Web Viewer or system browser covers it.
- Redesigns of the Welcome View beyond the settled prototype; richer interactive slots (inline library search, media-style tutorials) can layer on later without touching the trigger logic.
- The Zotero-side companion, and any onboarding for it.
- Backfilling changelog entries for releases that predate this feature.
- A "welcome" URI protocol action.
- A use-time warning when template features run against unmigrated legacy templates (e.g. a Notice during note import). Deferred as a follow-up once template loading knows about legacy files; the settings reminders carry that story for now.

## Further Notes

- Visual reference: the round-3 prototype (variant "Quiet-dismiss") under `.scratch/welcome-view/` — `round3.html` with its screenshot set in `shots/`. The prototype encodes the settled layout, states (fresh/upgraded × connected/missing/checking × light/dark), and component treatments; implementation translates it into the plugin's React + prefixed-Tailwind idiom rather than copying its mock markup.
- Domain vocabulary for this feature (Welcome View, Release Note, Migration Prompt, Legacy Data) is defined in the Obsidian app's context glossary; keep code and UI naming aligned with it.
- v1 eject facts (from v1 source): the eject action is a pure vault write and never saves settings, so an eject-only vault has no plugin settings file. Ejected files land in the hardcoded default `ZtTemplates` folder as `zt-<name>.eta.md` — `zt-note`, `zt-annot`, `zt-annots`, `zt-field`, `zt-cite`, `zt-cite2`, `zt-colored` — with no in-file marker; identity is folder + filename convention. v2 looks in its default `templates` folder for `zotlit-*.(liquid|eta).md`, so without detection these files are invisible on both folder and filename, and v2 silently uses built-in defaults.
- The mx (media-extended) plugin's release service is the pattern source: same two settings keys, same layout-ready timing, same first-install/upgrade split. Deviations are deliberate: a third branch for Legacy Data, until-acknowledged semantics for the Migration Prompt, no auto-opening of external pages, and the settings toggle actually exposed.
