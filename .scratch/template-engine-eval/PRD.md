# Liquid as default template language; Eta behind the JavaScript Templates gate

Status: ready-for-agent

See also: `findings.md` (evaluation + ratified decisions), `docs/adr/0004-liquid-default-eta-behind-javascript-templates-gate.md`, glossary terms **Template**, **JavaScript Templates**, **Filename Template**, **Managed Frontmatter** in `apps/obsidian/CONTEXT.md`.

## Problem Statement

ZotLit templates are shareable vault content, but today every Template — and every Managed Frontmatter expression — is arbitrary JavaScript executed with full plugin privileges. A user who pastes a template from a forum post is running unaudited code that can read and write their vault, reach the network, and (on desktop) touch the OS. Obsidian's plugin scorecard flags this as "dynamic code execution", and the Obsidian team's guidance to affected plugins (the Tasks precedent) is to ship such execution disabled by default behind explicit, non-syncable consent. Meanwhile, power users migrating from v1 depend on exactly that JavaScript expressiveness and must not be stranded.

## Solution

Templates render with Liquid by default — a pure interpreter with no dynamic code execution, covering all default templates and typical customization. Users who need JavaScript enable **JavaScript Templates**: a per-device, never-synced toggle behind a one-time confirmation modal, which activates Eta template files and JavaScript-mode Managed Frontmatter fields. Everything a template author sees — file naming, includes, helpers, whitespace control — behaves consistently across both languages, and a vault with JavaScript Templates disabled renders identically on every device — or refuses identically with an error naming the artifact, never rendering something else in its place.

## User Stories

1. As a new user, I want the default templates to work without enabling anything, so that I get literature notes out of the box with no security decision to make.
2. As a new user, I want templates to be unable to execute code by default, so that pasting a shared template from a forum can at worst produce wrong text, not compromise my vault.
3. As a template author, I want to customize note output in Liquid (`{{ zt.title }}`, `{% if %}`, `{% for %}`), so that I can shape my literature notes without learning JavaScript.
4. As a template author, I want per-tag whitespace markers (`{%-`, `-%}`) with no vault-level whitespace setting affecting Liquid, so that my template renders identically in any vault I share it with.
5. As a template author, I want a `{% liquid %}` statement block for logic-heavy sections, so that I can write indented, readable logic without leaking blank lines into my Markdown.
6. As a template author, I want a `{% bq %}…{% endbq %}` block tag, so that callouts and blockquotes get `>`-prefixed exactly like the current `bq()` helper.
7. As a template author, I want null and missing fields to render as empty strings and dates to render as local dates, so that Liquid output matches the current auto-filter behavior.
8. As a template author, I want link helpers to render by plain property access (`{{ a.fileLink }}`) and accept alias/subpath overrides via filters, so that links work in Liquid with the same data model the docs describe.
9. As a template author, I want an `embed` filter that prefixes `!` and collapses to nothing when the link is absent, so that image embeds need no guard.
10. As a template author, I want empty-string item fields to be absent (null) in template data, so that `{% if zt.comment %}` behaves the way I expect despite Liquid treating `""` as truthy.
11. As a template author, I want template errors reported with template name, line, and column, so that I can find and fix mistakes quickly.
12. As a template author, I want to override just one named Template (e.g. `annotation`) and have it included by the default `note`/`content` chain, so that small customizations don't require porting the whole set.
13. As a template author, I want to configure the new-note filename by editing a `filename` Template file in my template folder, so that filename logic lives with my other templates instead of buried in settings.
14. As a template author, I want the `suffix` helper available in the `filename` Template, so that colliding filenames get a random suffix only when needed.
15. As a power user, I want to enable JavaScript Templates and write Eta templates with full JavaScript, so that expressiveness beyond Liquid's ceiling stays available to me.
16. As a power user, I want my Eta and Liquid templates to include each other by name, so that I can keep most templates in Liquid and drop to JavaScript only where I need it.
17. As a power user, I want to mark individual Managed Frontmatter fields as JavaScript, so that computed frontmatter keeps its current power while my remaining fields stay portable Liquid.
18. As a power user, I want the existing Eta autoTrim setting to keep working for my Eta templates, so that my migrated v1 templates render unchanged.
19. As a cautious user, I want enabling JavaScript Templates to require a confirmation that states plainly what a template will then be able to do, so that I consent knowingly rather than by mis-click.
20. As a user who syncs my vault across devices, I want the JavaScript Templates flag to never sync, so that enabling it on one machine (or receiving someone else's config) cannot silently enable code execution on another.
21. As a user with JavaScript Templates disabled, I want an operation that needs an inert `.eta.md` template to fail with an error naming the file, so that I never get a note built from a template I didn't choose and know exactly what to fix.
22. As a user with both `zotlit-note.liquid.md` and `zotlit-note.eta.md`, I want the Liquid file to win with a warning about the shadowed Eta file, so that my notes render the same regardless of the device-local flag.
23. As a Managed Frontmatter user, I want each field to declare its expression language explicitly, so that my synced field configuration means the same thing on every device instead of being reinterpreted by a per-device flag.
24. As a Managed Frontmatter user, I want Liquid field expressions evaluated as value-expressions returning real types (arrays, numbers), so that frontmatter like tag lists stays structured YAML.
25. As a Managed Frontmatter user, I want a field whose expression throws at runtime to be skipped and reported per-field, so that one bad field doesn't abort the rest.
26. As a Managed Frontmatter user with JavaScript Templates disabled, I want note writes to fail with an error naming my JavaScript-mode fields rather than writing partial frontmatter, so that a synced field configuration never half-applies on a device that can't run it.
27. As a settings-UI user, I want frontmatter expression validation to check against the field's declared language, so that the editor flags mistakes in the language that will actually run.
28. As a settings-UI user with JavaScript Templates disabled, I want each JavaScript-mode field's row visibly marked as not working on this device, so that I can see at a glance which fields need the gate.
29. As a settings-UI user with JavaScript Templates disabled, I want new fields to be Liquid-only and existing JavaScript fields switchable only toward Liquid (their expression read-only until switched), so that a device that has never consented to code execution can never author or validate JavaScript.
30. As a security-conscious user, I want a device with JavaScript Templates disabled to never attempt dynamic code compilation or execution — rendering, migration, and settings validation included — so that the off state is absolute rather than best-effort.
31. As an upgrading alpha user, I want my existing frontmatter fields marked as JavaScript during settings migration — except untouched old defaults, which become the equivalent Liquid defaults — so that my custom expressions are never misread as Liquid and my stock fields keep working with the gate off.
32. As an upgrading alpha user, I want a release note explaining that my `template.filename` setting was dropped and how to recreate it as a `filename` Template file, so that I can restore my filename scheme in one step.
33. As a v1 migrant, I want the migration guide to include an Eta→Liquid translation table and the ejected Liquid defaults as a starting point, so that porting my custom templates is mechanical.
34. As a template author, I want to eject the embedded default templates as Liquid files, so that I can start customizing from a known-good base.
35. As a docs reader, I want the template documentation to teach Liquid as the only unqualified path, with JavaScript Templates as a clearly separated advanced section, so that the safe path is the obvious path.
36. As a plugin reviewer / security-conscious user, I want the plugin's dynamic-code disclosure to truthfully say execution is off by default and per-device opt-in, so that the risk statement matches reality.
37. As a power user with JavaScript Templates enabled, I want a language dropdown on each Template's settings row that sets up the chosen language's file for me, so that moving one Template to Eta (or back) doesn't require manual file surgery in the template folder.
38. As a power user switching a Template's language, I want a confirmation whenever the switch removes a file — and no dialog when it only creates one — so that I can't lose an authored template by mis-click while the reversible path stays frictionless.
39. As a user with JavaScript Templates disabled, I want the language dropdown to appear only where an inactive Eta file can be replaced by Liquid, so that my device can move templates toward the safe language but never author JavaScript.

## Implementation Decisions

- **Engine facade (primary seam).** The templates package exposes one dispatching engine surface: define/remove/render by Template name, with per-name language dispatch (Liquid vs Eta) decided by the registered source's language. Both languages' include mechanisms (`{% render %}` / `include()`) route back through this facade by name, so mixed-language sets work and include semantics live in exactly one place. This retires the Eta codegen-patching plugin as the owner of include semantics. The Obsidian host keeps injecting the managed-region wrap as a facade-level render transform, applied uniformly to both languages.
- **Liquid engine configuration** (fixed, not user-configurable; from the prototype): trimming off, `greedy: false` (a `-` marker trims up to one newline, preserving Markdown-structural blank lines), synchronous rendering, and an output-coercion hook reproducing the current auto-filter (null/undefined → `""`, `Temporal.Instant` → local date string, `toString()` for creators/ItemDate).
- **Liquid vocabulary**: a `bq` block tag wrapping the existing blockquote formatter; `embed` and link-override filters (`file_link`, `note_link`, `img_link`) that call the link-helper functions already on the data model; the `suffix` helper emitting the existing placeholder marker (post-render resolution unchanged); a date-format filter that understands the zt date shapes. Zero-argument link helpers need no filter — LiquidJS invokes function-valued properties on access (verified in the prototype).
- **Empty-string normalization**: the zt data layer emits `null` instead of `""` for empty item fields, so Liquid truthiness (`""` is truthy) matches author intuition. Behavior under Eta is unchanged (the auto-filter already renders null as empty, and JS truthiness treats both as false).
- **Dispatch and precedence**: the template file extension names the language (`zotlit-<name>.liquid.md` / `zotlit-<name>.eta.md`). When both exist for one name, the Liquid file wins and the Eta file is reported as shadowed. With JavaScript Templates disabled, `.eta.md` files are inert — never compiled — and a render dispatched to a name whose winner is an inert Eta file fails the operation with a typed error naming the file; there is no embedded-default fallback. Discovery is a log line; the settings row's warning and language dropdown are the at-rest visibility. The vault watcher tracks both extensions.
- **Template language dropdown**: each Template row in the setting tab carries a dropdown (**Liquid** / **JavaScript (Eta)**) reflecting the effective language. Nothing converts — the control replaces which language-edition file exists via vault file operations, leaving dispatch, Liquid-wins precedence, and the watcher untouched. Toward Eta: trash the Liquid edition if present; a pre-existing shadowed Eta file then takes over, otherwise a new Eta file is created from the embedded Eta default and opened in the editor. Toward Liquid: trash the Eta edition; the name falls back to the Liquid file or the embedded default. Visible only when the row has a legal other state: gate on → always; gate off → only on inert-Eta rows, offering Liquid alone. Confirmation exactly when a file is removed (all removals via Obsidian's recoverable trash); pure creation is dialog-free. The "(Eta)" parenthetical is specific to template files — the frontmatter field language control stays plain "JavaScript".
- **JavaScript Templates gate**: per-device flag stored through Obsidian's local-storage API (never in plugin settings data), off by default, flipped only through a settings control that opens a one-time confirmation modal on enable. This control is an exception to the declarative settings bridge and needs a custom-bridged row. All new UI strings go through Paraglide following Obsidian house style. Governing invariant: while the gate is off, the plugin attempts no dynamic code compilation or execution anywhere — rendering, migration, and settings validation included.
- **Managed Frontmatter**: each field is `{key, expr, merge, language}` with a required `language` of Liquid or JavaScript. An expression always evaluates in its declared language — the gate never reinterprets an expression, it only decides whether JavaScript fields run; pinning the language per field keeps a synced field configuration meaning the same thing on every device. Liquid fields evaluate as typed value-expressions preserving arrays and numbers (verified in the prototype). With the gate off, JavaScript fields are inert, mirroring the inert-Eta pattern: filtered out before compilation (upholding the invariant), and any note write that consumes the field set fails with the same typed error naming the JavaScript fields — no partial frontmatter writes, existing notes untouched. The exclusion is logged at compile time and the field's settings row carries a warning. Per-field runtime-error isolation and reporting stay as today: a field whose expression throws at runtime is skipped and reported per-field — that is the author's own bug surfaced loudly, distinct from the gate's silent policy substitution, which is what the blocking error forbids. The settings-UI validator compiles against the field's declared language; the "active language" concept (and its service getter) is retired. Modal rules — gate off: new fields Liquid-only, language switchable only JavaScript→Liquid, a JavaScript field's expression read-only until switched (key and merge stay editable); gate on: free toggle, JavaScript compile-validated at save. The default fields ship as explicit Liquid.
- **Inert-use error surface**: one typed error (`InertTemplateError`) owned by the template service, thrown at the two consumption seams — render dispatch to an inert Eta file, and the frontmatter-field accessor when the compiled set contains inert JavaScript fields (the accessor throws, so no consumer can forget the check). The error's message is the user-facing explanation naming the artifact; operation toasts surface it verbatim instead of the generic failure copy (the existing typed-error toast pattern). A batch update aborts on the first such error rather than repeating a configuration-level failure per item. No aggregated Notices, dedupe, or gate-round re-arm exist for inertness — the settings rows carry the at-rest warnings and discovery is logged.
- **Frontmatter settings migration**: the settings data version bumps to 2. The version-1→2 hook stamps `language: "javascript"` onto persisted frontmatter fields, except the three byte-exact old-default JavaScript expressions, which are rewritten to their Liquid-default equivalents. Version-0 data chains through the existing legacy hook (it had no frontmatter fields). Accepted consequences: an older build reading version-2 data runs on defaults for that session, and a hand-edited field missing `language` fails per-key validation, dropping the whole key to defaults — consistent with existing structured-key handling.
- **Filename Template**: becomes the sixth named Template, file-based with the same extension dispatch, restricted to item-own fields (no note-path resolvers), output trimmed to a single sanitized line, absent file → embedded Liquid default. The old filename setting key is removed without migration; the release notes carry the recreate-as-file instruction.
- **Embedded defaults**: both editions ship for all six templates — a `.liquid` and a byte-parity `.eta` edition each (the `filename` Eta edition recovered from the former `template.filename` setting default, `<%= zt.citationKey ?? zt.DOI ?? zt.title ?? zt.key %><%= suffix() %>`). The app bundles a `DEFAULT_TEMPLATES_ETA` map beside `DEFAULT_TEMPLATES`. Eject always writes the Liquid edition (the safe starting point; toward-Eta is how a row moves to Eta). Reset follows the file's own edition — an Eta row resets to the Eta default, surfaced only while JavaScript Templates is on; a lone inert `.eta.md` offers only the toward-Liquid dropdown, not reset. Liquid reset is gate-independent.
- **autoTrim**: unchanged semantics, but it configures only the Eta engine and its settings UI moves under the JavaScript Templates group. Liquid has no whitespace setting by design (template portability).
- **Single data vocabulary**: both engines bind template data to `zt` (Eta's `varName` is overridden from its default `it`), so `zt.…` is the only path vocabulary and the variable name is not a Liquid/Eta distinction. The Template Data Explorer offers one `Copy path (zt.…)` action regardless of the gate — the former separate "Copy Eta path (`it.…`)" item is removed (it emitted paths that are undefined in a real Eta template). Path syntax (`.name`, `[i]`, `["special-key"]`) is valid in both engines, so one copied path pastes correctly into either. There is no `it` alias; a stray `it.foo` fails loudly.
- **Docs**: the template-v2 documentation set is rewritten Liquid-first; JavaScript Templates get a separated advanced section covering the gate, Eta syntax, and the shadowing/inert rules.

## Testing Decisions

- Tests assert external behavior only: rendered output strings, returned frontmatter values, reported errors/warnings, and gate-dependent visibility — never engine internals, parse trees, or which code path rendered.
- **Engine facade tests** (templates package, pure Vitest): default-template output in Liquid (porting the existing default-template and cite-template test suites), byte-parity between the `.liquid` and `.eta` editions of all six defaults (the existing `defaults.test.ts` parity suite extended to cover `filename`), whitespace behavior per marker, `bq`/`embed`/link-filter/`suffix` behavior, output coercion, cross-language include chains (Liquid→Eta and Eta→Liquid by name), precedence when both sources are registered, Liquid frontmatter evaluation with typed results (per-field language dispatch, no JavaScript compilation for inert fields), and error positioning. Prior art: the existing engine, cite-template, and frontmatter test suites in the templates package.
- **TemplateService tests** (Obsidian app, existing `makeHarness` + `await using` harness with the obsidian mock): gate flag read/write via the local-storage API, `.eta.md` inert behavior when disabled (rendering a name whose winner is inert throws the typed error naming the file; no fallback output), shadowed-file warning when both extensions exist, watcher reactions to both extensions, filename Template resolution (file present / absent / inert Eta file → typed error), and per-field frontmatter language behavior end-to-end through settings (with the gate off the field accessor throws naming the JavaScript fields and existing notes stay untouched; with it on the fields evaluate). Prior art: the existing TemplateService suite. The version-1→2 frontmatter stamping/translation is covered in the settings migration suite, prior art: the existing legacy-migration tests.
- **Note-feature operation tests** (existing operations/update suites): the typed inert error surfaces its own message through the failure toast, and a batch update aborts on the first inert error instead of accumulating per-item failures. Prior art: the existing empty-filename typed-error toast tests.
- The confirmation modal's interior and Notice copy are not unit-tested (UI shell); their triggering conditions are tested at the service seam.
- The template language dropdown is settings-UI shell over plain vault file operations; the behaviors it rides on (extension dispatch, shadowing, gate inertness) are already covered at the service seam, so the dropdown's flows get no additional unit tests.

## Out of Scope

- Liquid editor autocomplete (deliberate follow-up issue; EtaSuggest remains, active only in `.eta.md` files).
- Sandboxing the Eta path (SES / ShadowRealm / wasm engines) — deferred pending Obsidian's possible official sandboxed-eval API; the gate leaves the seam.
- Automatic migration of the `template.filename` setting or automatic Eta→Liquid template conversion tooling (content translation — the language dropdown only replaces which edition file exists, it never translates a template).
- Grandfathering: no auto-enable of JavaScript Templates for vaults that already contain `.eta.md` files.
- Website content beyond the in-repo template documentation set.

## Further Notes

- Ship sequencing is one pre-beta milestone: engine + defaults + gate + docs land together so alpha users migrate once.
- Two decisions diverged from recommendations and are deliberate: dropping the filename setting without migration code, and shipping without Liquid autocomplete. Both are recorded in `findings.md`.
- The Managed Frontmatter language model was revised on 2026-07-11 from gate-switched (one language for the whole field set) to per-field explicit `language`, because the gate is per-device while the field settings sync — gate-switching made one synced configuration mean different things on different devices. Explicit over implicit throughout; ADR 0004 was amended in place.
- The inert-artifact behavior was revised on 2026-07-12 from degrade-and-notify (embedded-default fallback for Eta, skipped fields for frontmatter, aggregated Notices deduped per gate round) to blocking typed errors: an operation that requires an inert artifact fails, naming it. No implicit fallback — a device that can't run the user's code refuses rather than producing substitute output. The Notice/dedupe machinery was removed; settings-row warnings and a discovery log line remain. ADR 0004 amended in place; ticket 12 carries the implementation.
- The embedded-defaults and data-vocabulary decisions were revised on 2026-07-13. Both `.liquid` and `.eta` editions ship for all six templates (reversing "Liquid only" and the out-of-scope line), so switching a Template to Eta starts from the Eta default rather than a blank file; the `filename` Eta edition is recovered from the former `template.filename` setting default. Separately, both engines already bind data to `zt` (Eta `varName` overridden from `it`), so the single `zt.…` vocabulary is affirmed and the Data Explorer's separate "Copy Eta path (`it.…`)" item — which emitted paths undefined under Eta — is removed. ADR 0004 amended in place.
- The Obsidian scorecard's "dynamic code execution" flag will remain (static analysis keys on code presence); the accepted posture is off-by-default plus disclosure, per the Tasks precedent.
- The evaluation prototype (`proto/liquid-proto.mjs`) demonstrates the Liquid ports of all default templates and the decisive engine behaviors; it is reference material, not shipped code.
