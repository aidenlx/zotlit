## Note and content templates [#note-and-content-templates]

The `zt` root for the `note` template: every item field plus the runtime-computed fields assembled at the app layer (backlinks, resolved attachment links, flattened annotations, author conveniences).

The note body of a Profile document, and the `{% managed %}` block inside it, share this context.

## Annotation template [#annotation-template]

The `zt` root of the `annotation` template: one annotation ([`TemplateAnnotation`](#annotation-entry)) plus [`citation`](#annotation-template-citation). Entries of `zt.annotations` on the note root carry no citation — only the single-annotation render resolves one.

The Annotation Section of a Profile document receives a single annotation as `zt`.

## Filename template [#filename-template]

The `zt` root of the `filename` template: an item's own fields, its collections, Primary Creators, an Author Summary, and inert `notePath` / `noteLink` stubs. It reads only this item when naming a note.

The `filename` template in a Profile document's manifest receives exactly the properties below.

## Item fields [#item-fields]

Every Zotero item field is a flat property on `zt`. The canonical Zotero field name is the primary accessor, and type-specific spellings normalize to their canonical base field: reach `blogTitle` as `zt.publicationTitle` and `studio` as `zt.publisher`. The type-specific spelling itself is not on `zt`.

## Citation template [#citation-templates]

The citation-template data root (`zt`): `citations[i].item === items[i]`.

The citation template (`zotlit-citation.md`) renders one in-text citation.

Pass `zt.citations` to the Pandoc Citation formatter, which reads `prefix`, `suffix`, `suppressAuthor`, `locator`, and `labelShort`, and omits entries whose `item.citationKey` is null.

| Language | Form                    | Expression                                                   |
| -------- | ----------------------- | ------------------------------------------------------------ |
| Liquid   | `normal`                | `{{ zt.citations \| pandoc_cite }}`                          |
| Eta      | `normal`                | `<%= pandocCite(zt.citations) %>`                            |
| Liquid   | `prefer-author-in-text` | `{{ zt.citations \| pandoc_cite: "prefer-author-in-text" }}` |
| Eta      | `prefer-author-in-text` | `<%= pandocCite(zt.citations, "prefer-author-in-text") %>`   |

<ContractTable section="citation-templates" />

### Citation variants [#citation-variant]

The gesture a Citation was requested with, handed to the Citation Template as `zt.variant`: `"main"` for Enter, `"alt"` for Shift+Enter or a trailing `/` in the suggester query. The enum names the gesture alone — the Citation Template decides what each variant renders.

The built-in citation template renders the author-in-text form for `alt` and the bracketed form for `main`.

- `"main"`: Enter in the suggester, the insert modal, and an annotation's `citation`.
- `"alt"`: Shift+Enter, or a trailing `/` in the suggester query.

### Citation item [#citation-item]

One cited item within a Citation: the pure item data plus the citation-scoped properties, which never live on the item. Exposed to the Citation Template as `zt.citations`, with `zt.items` the same items bare.

Each entry in `zt.citations`. Loop over them with `{% for citation in zt.citations %}`.

<ContractTable section="citation-item" />

### Cited item fields [#cited-item-fields]

A cited item's data, in the same template vocabulary as the note root and narrowed to the fields both a live Zotero item and a note's embedded CSL-JSON snapshot supply. Vault and library context — tags, dates-added/modified, library identity, and the note resolvers — stays on the note root, which the embedded snapshot cannot express. An unresolved reference becomes a stub with every field null, so a citation template never null-checks the item itself.

Each cited item also carries every [item field](#item-fields) of its type. The note-root properties it leaves behind are `key`, `libraryID`, `indexedKey`, `tags`, `dateAdded`, `dateModified`, `collections`, `backlink`, `weblink`, `annotations`, `attachments`, `authors`, `authorsShort`, `relatedItems`, `notes`, `notePath`, and `noteLink`.

## Annotation types [#annotation-types]

A resolved annotation type name: one Zotero declares, or `"unknown"` for a type id Zotero added after this mapping was written.

- `"highlight"`: Text marked with a highlight color.
- `"note"`: A note pinned to a spot on the page.
- `"image"`: A rectangular area selection, saved with an excerpt image.
- `"ink"`: A freehand drawing, saved with an excerpt image.
- `"underline"`: Underlined text.
- `"text"`: Free text typed onto the page.
- `"unknown"`: A type id Zotero added after this mapping was written.

## Parent item [#parent-item]

Parent literature item as seen from the standalone `annotation` template. The annot-view drag-insert resolves the item's tags but omits collection rows entirely — `collections` lives only on the note root. Read them there (`zt.collections`).

<ContractTable section="parent-item" />

## Creators [#creators]

One creator of an item, in the template vocabulary. Coerces to [`fullName`](#creators-fullName) in string contexts.

`zt.creators` lists every creator on the item. `zt.authors` lists the creators in the first populated role: the item's primary creator role, editor, director, then contributor. Institutional creators (Zotero `fieldMode=1`) set `literal` and leave `family` and `given` empty.

<ContractTable section="creators" />

## Tags [#tags]

A Tag in the template vocabulary. Coerces to `name` in string contexts (like a collection coerces to its name), so `{{ zt.tags | join: ", " }}` renders tag names directly. Zotero-internal IDs are dropped; `type` is the resolved name rather than Zotero's raw int.

<ContractTable section="tags" />

## Collections [#collections]

A Zotero collection an item belongs to, in the template vocabulary. Coerces to `name` in string contexts (like a tag coerces to its name).

Use the `collection_paths` filter to render the full ancestor path joined by a separator (`"/"` by default).

<ContractTable section="collections" />

## Date format [#date-format]

`zt.date` is one of four parsed variants, discriminated by `kind`. `{{ zt.date }}` renders an ISO date for `"date"`, an ISO year-month for `"yearMonth"`, a bare year for `"year"`, and the raw user text for `"text"`. Use `{{ zt.date | date: "%Y-%m-%d" }}` for explicit formatting with [strftime tokens](/docs/reference/templates/syntax#date-formatting-filter); a `"text"` date renders its raw text unchanged whatever the format string.

<ContractTable section="date-format" />

## Extra field [#extra-field]

Best-effort structured view of Zotero's `extra` field. Plain data so it is directly indexable in Liquid, Eta, and JS.

`toString` is non-enumerable, so a spread, `JSON.stringify`, or `Object.keys` sees the three data properties alone.

`zt.extra` is a parsed view of Zotero's free-text Extra field, or `null` when the field is empty. `{{ zt.extra }}` renders the raw field text.

<ContractTable section="extra-field" />

### Extra lines [#extra-lines]

One source row of an Extra field, in document order: a parsed pair (`key` plus trimmed `value`) or a non-pair text/blank row (`key: null`). `raw` is the verbatim line so interleaved prose is never dropped.

A line splits on its first `:` or `=`, and is a pair only when the key starts with an ASCII letter and otherwise holds ASCII letters, digits, spaces, dots, hyphens, or underscores. A line that does not match, and one whose value is empty, becomes a text row.

A non-enumerable `toString` returns `raw`, as on the extra field itself.

Each entry of `zt.extra.lines`.

<ContractTable section="extra-lines" />

## Related items [#related-items]

A single entry in [`relatedItems`](#note-and-content-templates-relatedItems): the related item's own fields, flattened with its backlink and author conveniences. Depth-1 — its own `annotations`, `attachments`, and `relatedItems` are deliberately absent (resolving them would require a per-related-item DB fan-out), marking the boundary of the relation graph.

Each entry also carries every [item field](#item-fields).

<ContractTable section="related-items" />

## Notes [#notes]

A child note exposed on [`notes`](#note-and-content-templates-notes) as a link only — the imported note's Markdown body lives in its own file, never inlined here. Carries a non-enumerable `toString` rendering its [`title`](#notes-title) (falling back to [`key`](#notes-key)), so it stringifies to a title in string contexts and previews.

See [Import Zotero notes](/docs/how-to/import-zotero-notes) for the import workflow.
