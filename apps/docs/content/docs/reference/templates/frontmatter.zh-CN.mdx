本页介绍了 ZotLit 如何管理文献笔记顶部的 YAML frontmatter 属性：包含 Zotero 拥有的系统字段、配置方案声明的受管字段、属性合并策略以及笔记更新时的具体行为。

分步配置指南请参阅[配置 frontmatter 属性](/docs/how-to/configure-frontmatter-properties)。

## 系统保留字段

ZotLit 自身负责写入这些配置键。受管 frontmatter 绝不能以它们为目标进行覆盖。

| 字段             | 数据源                 | 说明                                                                           |
| ---------------- | ---------------------- | ------------------------------------------------------------------------------ |
| `zotero-key`     | `zt.indexedKey`        | 文献笔记的唯一身份标识：对于“我的文库”为 `KEY`，对于群组文献库为 `KEYgGROUPID` |
| `zotlit-profile` | 执行当前操作的配置方案 | 生成该笔记的配置方案名称及 12 位 ID。由默认配置方案生成时留空不显              |
| `zotlit-csl`     | 配置方案绑定的引文样式 | 该笔记的引文和参考文献渲染所采用的 CSL ID。当配置方案未绑定样式时留空          |

## 用户自定义字段

受管 frontmatter 属于[配置方案文档](/docs/reference/templates/profile-document)的 manifest 中 `frontmatter` 键下的有序配置列表。每个配置项可生成单个属性，或一次性展开生成多个属性。

您可以在模板工作台的 <UiLabel name={m.workbench_tab_properties()} /> 标签页中直观编辑该列表。在 <SettingsPath /> 的 <UiLabel name={m.settings_profile_document_name()} /> 所在行，选择 <UiLabel name={m.settings_profile_edit()} /> 即可进入。

每个配置项包含一个可选的 `key`、一个可选的 `merge` 合并策略，以及恰好一个值计算成员。成员名称本身即声明了所使用的计算语言，因此配置项无需额外的语言标识：

| 成员字段 | 是否必填 | 说明                                                                                          |
| -------- | -------- | --------------------------------------------------------------------------------------------- |
| `key`    | 否       | 写入笔记的 YAML 属性名。展开项（spread entry）可省略此字段                                    |
| `expr`   | 三选一   | Liquid 值计算表达式                                                                           |
| `value`  | 三选一   | JSON-e 模板                                                                                   |
| `js`     | 三选一   | JavaScript 表达式。在关闭 JavaScript 模板权限时处于休眠状态                                   |
| `merge`  | 否       | 笔记更新时该字段的应用策略。支持 `replace`（默认覆盖）、`append`（追加）或 `keep`（保留现有） |

一个完整写出 `key`、`value` 和 `merge` 的标准配置项示例：

```yaml
frontmatter:
  - key: citekey
    value: { "$eval": "zt.citationKey" }
    merge: replace
```

编辑器中的 <UiLabel name={m.workbench_properties_format()} /> 控件对应了不同的值成员：<UiLabel name={m.workbench_properties_format_value()} /> 写入 `expr`，<UiLabel name={m.workbench_properties_format_rule()} /> 写入 `value`，而 <UiLabel name={m.workbench_properties_format_text()} /> 则写入按纯文本保存的 `value`。带有 `js` 的配置项可在 <UiLabel name={m.workbench_advanced()} /> 源码视图中直接编辑。

`value` 可以以任何标准的 YAML 语法编写，例如在[展开项（Spread entries）](#spread-entries)中的块映射形式。当您在可视化编辑器中编辑 `value` 时，工作台会将其作为单行 JSON 保存至配置方案文档中，其他配置项则保持原样。

### 展开项（Spread entries） [#spread-entries]

没有声明 `key` 的配置项称为展开项。其 `value` 或 `js` 成员求值结果为一个对象映射（mapping），其中的每个键都会作为独立属性字段注入到该配置项所在位置，并统一应用该配置项的合并策略。

```yaml
frontmatter:
  - value:
      title: { "$eval": "zt.title" }
      "zotero/${zt.itemType}": true
```

Inside a spread mapping, a false `$if` omits that key and leaves the note's value alone. `${}` interpolation builds a key name. A top-level `$let` shares one calculation across every produced field. A `$if` that is false at the root of the entry contributes an empty patch, so the entry writes nothing.

`expr` always produces a single value, so a spread entry cannot use it: a keyless `expr` entry fails validation. A spread entry whose result is not a mapping, or that produces a reserved or empty key, refuses the whole operation. Diagnostics name the entry by its 1-based position in the list.

In the editor, <UiLabel name={m.workbench_properties_add_spread()} /> adds a spread entry. Its row reads <UiLabel name={m.workbench_properties_spread()} /> and lists the properties it produced.

### Default fields

Out of the box, the Default profile declares four entries. Its document reads:

```yaml
frontmatter:
  - key: title
    expr: zt.title
    merge: replace
  - key: related
    expr: zt.relatedItems | note_links
    merge: replace
  - key: collections
    expr: zt.collections | collection_paths
    merge: replace
  - key: citekey
    value: { "$eval": "zt.citationKey" }
    merge: replace
```

The `citekey` entry writes `citekey: null` when the Zotero item has no citation key. All four are ordinary managed frontmatter. You can edit or remove them like any other entry.

### Liquid expressions

An `expr` member is one value expression, not a template block. It uses the same filter vocabulary as templates (see [Template syntax](/docs/reference/templates/syntax)) and returns typed values (arrays, numbers, strings), not rendered text.

```
zt.title                              -> "My Paper Title"
zt.authors | join: ", "               -> "Jane Smith, Bob Jones"
zt.tags | map: "name"                 -> ["methodology", "open access"]
zt.tags | obsidian_tag                -> ["methodology", "open_access"]
zt.collections | collection_paths     -> ["Project/Reading", "Research"]
zt.date.year                          -> 2023
```

### JavaScript expressions

A `js` member holds a JavaScript expression. It requires the [JavaScript Templates](/docs/concepts/javascript-templates) gate. Any valid JavaScript expression works, with the full note context available as `zt`:

```
zt.authors.map(c => c.fullName)   -> ["Jane Smith", "Bob Jones"]
zt.tags.map(t => t.name)          -> ["methodology", "review"]
zt.date?.year                     -> 2023
```

The return value is serialized to YAML automatically.

## Merge strategies

Each entry selects one merge strategy, set with <UiLabel name={m.workbench_properties_merge()} /> in the editor:

| Strategy  | Editor option                                             | Behavior                                                                                                                                                                                                                                                                                            |
| --------- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `replace` | <UiLabel name={m.workbench_properties_merge_replace()} /> | Writes the generated value unconditionally. The existing value is overwritten                                                                                                                                                                                                                       |
| `append`  | <UiLabel name={m.workbench_properties_merge_append()} />  | Appends new generated values not already present to the existing array. Manual additions remain. If existing is blank, writes the generated value. Both the existing and generated values must be arrays; when either side is not an array (and existing is not blank), the field is left unchanged |
| `keep`    | <UiLabel name={m.workbench_properties_merge_keep()} />    | Writes the generated value only when the existing field is blank. Once the field has a value, it is never overwritten                                                                                                                                                                               |

### Absent values

Only a `value` entry can produce absence. A JSON-e template that renders nothing at its root, such as one whose top-level `$if` is false, contributes no value at all.

Absence is the one way to delete a managed key. Under <UiLabel name={m.workbench_properties_merge_replace()} /> an absent value deletes the existing key; under <UiLabel name={m.workbench_properties_merge_append()} /> and <UiLabel name={m.workbench_properties_merge_keep()} /> it leaves the key as it stands.

### What counts as blank

A value is blank (and treated as absent by <UiLabel name={m.workbench_properties_merge_append()} /> and <UiLabel name={m.workbench_properties_merge_keep()} />) when it is:

- `null` or undefined
- An empty string (`""`)
- An empty array (`[]`)
- An empty plain object (`{}`)

### Undefined expressions

When a Liquid or JavaScript expression returns `undefined`, the field is untouched regardless of the merge strategy. Only defined values (including explicit `null`) reach the merge logic.

### Append arrays detail

The <UiLabel name={m.workbench_properties_merge_append()} /> strategy preserves existing items verbatim (including any duplicates already present) and appends only generated items not already in the array.

## Reserved keys

ZotLit refuses a static key, or a key a spread entry produces, from this set:

| Key               | What it protects                                                                                                  |
| ----------------- | ----------------------------------------------------------------------------------------------------------------- |
| `zotero-key`      | Literature note identity. The item key, with the group library ID appended for group libraries                    |
| `zotlit-profile`  | The profile stamp that records which profile produced the note. Absence selects the Default profile               |
| `zotero-note-key` | Identity of an imported child note. Kept apart from `zotero-key` so the note never registers as a literature note |
| `zotero-lastmod`  | The source child note's `dateModified`, which batch re-import reads to skip unchanged notes                       |
| `zotlit-csl`      | The CSL style ID one note's citations and references render with, set from the profile's citation style           |

A profile document that declares a reserved or duplicate static key fails to load, and ZotLit excludes it from the profiles it offers instead of repairing it. See [Profiles](/docs/concepts/profiles).

## Validation

The <UiLabel name={m.workbench_tab_properties()} /> tab marks the row that failed with <UiLabel name={m.workbench_properties_row_problem()} />, and the row shows what went wrong in place of a value. The full explanation, which names the failing key and the entry's position, is in the <UiLabel name={m.workbench_problems_heading()} /> area of the editor.

Validation has three stages:

1. **The document.** A reserved static key, a duplicate static key, or a keyless `expr` entry stops the document from loading.
2. **The expression.** An `expr` or `js` member that fails to compile, or a `value` that cannot evaluate, is a problem the editor names by key and entry position.
3. **The write.** A `value` or `js` entry whose result falls outside the frontmatter value domain, a spread entry that produces no mapping, or a produced key that is reserved or empty refuses the whole operation.

A refused operation writes nothing. ZotLit never applies a partial patch to a note. A `js` entry that is inert while the gate is off refuses by key, or by entry position when the entry is keyless.

## Merge on update

When you run <Command inline name={m.command_update_note_name()} /> or <Command inline name={m.command_update_note_metadata_name()} />, ZotLit refreshes frontmatter:

1. **Managed entries** are re-evaluated in the order they appear in the `frontmatter` list of the [profile document](/docs/reference/templates/profile-document) and applied with their merge strategy.
2. **System identity** (`zotero-key`) is refreshed.
3. **Unmanaged keys:** any frontmatter key not in the managed set (e.g. `aliases`, `tags`, `cssclasses`) is preserved. ZotLit never touches keys it does not own.

<Command inline name={m.command_overwrite_note_name()} /> replaces the note body
but applies the same frontmatter behavior: managed keys are refreshed and
unmanaged keys are kept.

ZotLit writes frontmatter through Obsidian's `processFrontMatter` API, which preserves key ordering and formatting for unmanaged keys. On a newly created note, managed fields are written in the order they appear in the profile document's `frontmatter` list, followed by system fields. An entry later in the list wins the value, because each entry is applied over the value the entries before it produced.

Removing `citekey` or another entry from the `frontmatter` list does not delete existing values. Those values become unmanaged and remain in the note.

## JavaScript Templates gate

The [JavaScript Templates](/docs/concepts/javascript-templates) gate controls whether `js` entries run:

- **Gate off:** `js` entries are inert. They are not evaluated. Any operation that depends on an inert entry surfaces an error naming those keys. `expr` and `value` entries are unaffected.
- **Gate on:** `expr`, `value`, and `js` entries evaluate normally.

The gate never reinterprets a member. An `expr` entry always evaluates as Liquid, and a `js` entry always evaluates as JavaScript.

A spread entry that uses `js` is refused by its entry position while the gate is off, because its keys cannot be known until it runs.

<Callout type="warn" title="Inert entries block note operations">
  When any frontmatter entry uses the `js` member and the gate is off,
  literature note creation and update fail with an error listing the inert keys.
  Either enable the gate or rewrite those entries as `expr` or `value`. See
  [Enable JavaScript templates](/docs/how-to/enable-javascript-templates).
</Callout>
