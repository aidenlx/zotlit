在提交 Bug 反馈时，通常需要附带模板错误报告、ZotLit 插件日志、Obsidian 系统日志，或是来自配套插件 ZotLit Companion 的 Zotero 调试输出。下方的每个章节均独立成篇，您只需按照反馈中所要求的项进行操作即可。

获取到日志后，请在 GitHub 的 [Bug reports 讨论区](https://github.com/aidenlx/zotlit/discussions/categories/bug-reports)中提交反馈。

<Callout type="warn" title="跨端组件问题需要双侧日志">
  如果问题涉及 ZotLit 与 Companion
  两端（例如数据同步、即时更新、笔记导入或任何依赖 Zotero
  运行的操作），请在复现问题之前，**同时**完成[ZotLit 日志](#zotlit-logs)与
  [Zotero
  调试输出](#zotero-debug-output)中的配置步骤。复现一次后，分别保存两端的日志输出。
</Callout>

## 模板错误报告 [#template-error-report]

当在模板工作台中预览失败时收集此报告。报告中记录了模板引擎自身的报错信息以及失败尝试的上下文，以便他人能够准确排查定位具体故障。

<Steps>
  <Step>
    ### 打开问题面板

    在模板工作台中，点击预览区域中或源码标记上的 <UiLabel name={m.workbench_problem_show()} />。<UiLabel name={m.workbench_problems_heading()} /> 区域会展示失败原因。

  </Step>
  <Step>
    ### 复制错误报告

    点击 <UiLabel name={m.workbench_problems_copy()} />。如果您希望在复制前先阅读报告内容，可先展开 <UiLabel name={m.workbench_problems_technical()} />。

    该报告包含引擎报错消息、错误名称、触发诱因、相关源码摘录以及引擎给出的具体报错位置。此外，它还会记录失败时间戳、是自动检查还是通过 <UiLabel name={m.workbench_preview_run()} /> 触发、对应的模板文档与章节、模板语言、预览数据根节点选项、当前选中的条目或示例、源码版本以及 ZotLit 和 Obsidian 的版本号。失败尝试无法获取的值将显示为 `unavailable`。

  </Step>
  <Step>
    ### 粘贴到反馈中

    将复制的文本直接粘贴到您的 Bug 报告中。在您主动粘贴提交之前，任何信息都不会离开您的本地仓库。

  </Step>
</Steps>

<Callout type="info" title="报告不会因后续修复而丢失">
  您可以继续在模板上修改代码。已复制的报告严格记录了当时发生失败的那次尝试，因此后续的编辑或切换条目不会改变它。在成功修复后，展开的{" "}
  <UiLabel name={m.workbench_problems_heading()} /> 区域还会提供{" "}
  <UiLabel name={m.workbench_problems_copy_last()} />
  ，便于您获取先前阅读的那次故障记录。
</Callout>

<Callout type="info" title="Ask the community">
  <UiLabel name={m.workbench_problems_community()} /> sits beside the copy
  action and opens the [community page](/community). It opens a page; it sends
  nothing.
</Callout>

### When to add more evidence

The copied report covers one failed template attempt. Collect one of the following as well when it applies:

- **[ZotLit logs](#zotlit-logs)**: the failure has no engine message, or it happens while creating or updating a note rather than in the preview.
- **[Template data](#template-data)**: the template rendered without failing, but produced the wrong content.
- **[Obsidian debug info](#obsidian-debug-info)**: the problem may involve another plugin, a theme, or a specific Obsidian build.

Each one is a separate collection step. The copied report never carries a log archive or a template-data export.

## ZotLit logs

<Steps>
  <Step>
    ### Open the Advanced settings

    In Obsidian, open <SettingsPath page={m.settings_page_advanced()} /> and find the <UiLabel name={m.settings_advanced_logging_heading()} /> group.

  </Step>
  <Step>
    ### Turn on debug logging

    Set <UiLabel name={m.settings_log_level_name()} /> to **debug**, then turn on <UiLabel name={m.settings_log_to_file_name()} />. Logs now append to `zotlit.log.jsonl` inside the plugin folder.

  </Step>
  <Step>
    ### Reproduce the problem

    Do whatever triggers the bug.

  </Step>
  <Step>
    ### Save the log archive

    Back in <SettingsPath page={m.settings_page_advanced()} />, select <UiLabel name={m.settings_log_export_name()} />. This exports the log file for sharing.

  </Step>
  <Step>
    ### Upload the archive

    Attach the saved archive to your bug report.

  </Step>
</Steps>

<Callout type="info" title="Turn logging back off">
  Set <UiLabel name={m.settings_log_level_name()} /> back to **info** and turn
  off
  <UiLabel name={m.settings_log_to_file_name()} /> once you no longer need
  ongoing logging.
</Callout>

## Template data [#template-data]

Collect this when a template rendered the wrong thing. The saved file holds the exact data your templates received for one item.

<Steps>
  <Step>
    ### Open the explorer on the item

    [Open the Template Data Explorer](/docs/how-to/explore-template-data) on the item that reproduces the problem.

  </Step>
  <Step>
    ### Anchor at the annotation

    If the problem is in an annotation template, open the more-options menu on that annotation node in the tree and select <UiLabel name={m.workbench_explorer_menu_explore_annotation()} />. For any other template, skip this step and stay at the note root.

  </Step>
  <Step>
    ### Save the template data

    Open the more-options menu on the explorer's tab and select <UiLabel name={m.template_data_explorer_menu_export_json()} />. This downloads a file named like `zotlit-template-data-ABCD2345-20260512-143000.json`.

    The file always holds the whole current root: the full note template data at the note root, or the annotation's data when the explorer is anchored at an annotation. A filter in the explorer does not narrow it.

  </Step>
  <Step>
    ### Upload the file

    Attach the saved file to your bug report.

  </Step>
</Steps>

<Callout type="warn" title="Read the file before you share it">
  The file contains Zotero library metadata for the item, absolute paths to
  attachments inside your Zotero data folder, and your Zotero account username.
  Review it before you attach it to a public bug report.
</Callout>

<Callout type="info" title="Placeholder markers are expected">
  The explorer never writes files into your vault, so helpers that normally
  create them, such as annotation excerpt images and imported child notes,
  produce placeholder markers instead of real links. These appear as `$inert`
  entries in the file, and helpers appear as `$helper` entries. Both are
  expected in the saved data.
</Callout>

## Zotero debug output

<Steps>
  <Step>
    ### Set the Companion's log level

    In Zotero, open **Edit > Settings** (Windows/Linux) or **Zotero > Settings** (macOS), then select the <UiLabel name={m["zotero.prefs_pane_label"]()} /> pane. Set <UiLabel name={m["zotero.prefs_logging_level"]()} /> to <UiLabel name={m["zotero.prefs_log_level_debug.label"]()} />.

  </Step>
  <Step>
    ### Restart Zotero with logging enabled

    Go to **Help > Debug Output Logging** and click **Restart with Logging Enabled…**.

    <Callout type="warn" title="Do not use troubleshooting mode">
      A confirmation dialog appears. Do not select **Restart in Troubleshooting Mode**: that mode disables all add-ons, including the Companion, so no debug output would be captured.
    </Callout>

  </Step>
  <Step>
    ### Reproduce the problem

    As soon as Zotero restarts, reproduce the problem.

  </Step>
  <Step>
    ### Open the debug output viewer

    Go to **Help > Debug Output Logging > View Output**.

  </Step>
  <Step>
    ### Save the output

    In the viewer, go to **File > Save…**, choose Format: **Text Files**, and save the output.

    Do not use **Submit Output** or **Copy to Clipboard**. The full log file is needed.

  </Step>
  <Step>
    ### Upload the file

    Attach the saved text file to your bug report.

  </Step>
</Steps>

<Callout type="info" title="Reset the log level">
  Set the Companion's <UiLabel name={m["zotero.prefs_logging_level"]()} /> back
  to its previous value after collecting the output.
</Callout>
