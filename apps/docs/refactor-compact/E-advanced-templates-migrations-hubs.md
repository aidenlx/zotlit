## how-to/edit-a-profile-as-markdown.mdx
- Title: Edit a profile as Markdown | Description: Open a profile document as Markdown, follow the shape ZotLit enforces, and read the faults the Problems area reports.
- Archetype: How-to (opening steps) + Reference (shape rules, Problems table)
- Purpose: type a profile document directly instead of using Workbench tabs; know the enforced rules; decode Problems entries.
- Prerequisites stated: none
- Product facts:
  - A profile is an ordinary vault note; ZotLit keeps it editable even while reporting a fault; never rejected, text never lost.
  - Two routes to Markdown from Workbench: Advanced toggle (whole doc in one editor), or pane menu Open as Markdown (saves doc first, then switches that pane to Obsidian's Markdown editor). Or open file from file explorer like any note.
  - Return: view header "Open in Workbench" reopens the same doc with preview and problems.
  - Document = four parts in order: manifest, note source, optional managed block, Annotation Section.
  - CHANGED (#1687; reference/templates/profile-document on next): zero managed blocks is valid, and the document you get when you customize or duplicate the Default profile has none (built-in default body renders once, at creation). Updating a note that still has `%%zt-managed%%` markers under such a document refreshes frontmatter only and shows m.notice_updated_note_no_managed_block; add a `{% managed %}` block to re-render the region. Default content section (reference/templates/defaults#content-template) is now just `## Annotations` + the `zotquery` block, written in place, no Notes list.
  - Rules: first line exactly `---`, one later `---` closes manifest; `id` = 12 letters/digits, unique among profile docs in the folder (profiles sharing an ID are ALL excluded from ZotLit); note source holds at most one managed block `{% managed %}`...`{% endmanaged %}` (ZotLit re-renders that block alone on note update, rest of source left as written); exactly one `--- zotlit:annotation ---` line, after the note source; doc with `id: default` carries neither Match conditions nor bindings; properties ZotLit writes belong in the manifest, not in a note.
  - Problems area is at bottom of Workbench pane, lists each fault with suggested recovery, recomputes while editing, entry clears when rule no longer broken.

- Title: Enable JavaScript templates | Description: Turn on the JavaScript Templates gate so Eta template documents and `js` frontmatter entries run on this device.
- Archetype: How-to (with Explanation lead-in)
- Purpose: turn the per-device JS gate on/off.
- Prerequisites stated: none (callout says read the concept page first)
- Product facts:
  - JavaScript Templates gate is per-device, disabled by default.
  - 2.1: language in filename (`zotlit-note.eta.md` Eta, `zotlit-note.liquid.md` Liquid). 2.2: template document declares `language: eta` in its own manifest.

  - Turn off: one click, no confirmation modal, immediate; every `language: eta` doc inert, `js` entries stop evaluating until re-enabled.
  - Stored locally per device outside synced plugin data; enabling on one device doesn't enable on another.
- Steps: 1 Settings > Advanced; find Template engine group and JavaScript Templates row. 2 Click Turn on; confirmation modal (title + warning body quoted) appears; click confirm action. Turn off: same group, click Turn off.

## concepts/profiles.mdx
- Title: Profiles | Description: What a literature note profile is, how ZotLit chooses one for an item, and how a note keeps the one that made it.
- Archetype: Explanation
- Purpose: understand what a profile is, how it is selected, stamped on notes, and when a note changes profile.
- Prerequisites stated: none
- Product facts:
  - A profile is the document deciding name, folder, properties, body, and annotation format of notes written from it.
  - File `zotlit-profile.<slug>.md` in the folder named by "Template folder" setting. ZotLit reads every direct child whose name starts `zotlit-profile.`; nothing registers/installs/points at it; dropping the file in is enough.
  - Filename is not identity; renaming file changes nothing; manifest `id` is identity and what a note remembers.
  - Default profile exists in every vault without a document: built-in template + vault-wide defaults held as settings. Customizing writes `zotlit-profile.default.md`; afterward it's a document like any other. Default is fallback: note with no profile of its own belongs to Default; an added profile that leaves something unset inherits from Default (profile states only differences).
  - Selection order: 1 profile chosen for that operation; 2 profile named by a command or Companion link; 3 profile whose Match conditions accept the item; 4 Default. Steps 1-2 each cover single operation; Match conditions live in profile doc; profile without them never selected on its own; exactly one match -> used without asking; several match -> ZotLit stops and asks which.
  - Stamp: note records profile in `zotlit-profile` property as name plus ID, e.g. `Books (V1StGXR8Z5jd)`; only ID compared; name is a hint refreshed next write; renaming label or file breaks nothing. Default-written note has no such property (absence = Default). Imported notes carry stamp from the operation or literature note that created them.
  - Two docs claiming same ID are both left out of registry rather than repaired; not offered anywhere until one gets unique ID.
  - Update does not re-run conditions: renders with stamped profile; other notes untouched. Editing conditions/adding profile changes future notes only. A command naming a profile the note doesn't carry is refused with notice m.notice_literature_note_profile_conflict.
  - Moving a note to another profile is a deliberate action, never a side effect; asks confirmation first; leaves text outside managed region as is; next update renders from the new profile. (#1687: "renders" covers the frontmatter and, only when the note has a managed region and the new profile a managed block, that region; a default-made note's body is never re-rendered by update. VERIFY profile switch on a region-less note.)
  - No per-note template: editing the profile doc changes all its notes at their next update. Default notes follow Default doc (exists only after customizing) else built-in template.

- UI labels: Template folder (m.settings_template_folder_name); conflict notice (m.notice_literature_note_profile_conflict)

- Archetype: Explanation
- Purpose: understand the agent-facing CLI, skill, guide, command groups, read/write boundaries, JS gate and frontmatter handling.
