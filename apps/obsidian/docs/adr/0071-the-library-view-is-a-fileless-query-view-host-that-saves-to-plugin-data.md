# The Library View is a fileless Query View host that saves to plugin data

The Library View is a fourth host of the one Query View (ADR 0069), with no Query File and no Query Context. What it shows is its Library View Document: the Library Tree node, the Reading State facets, the search text and the sort. The document is saved per vault under one SettingsService key, `library.document`, in `data.json`. The Query View's text derives from the document; a toolbar change comes back as new text, from which the host takes the sort into the document. The host's `save` writes the key through the SettingsService and then awaits the write, so a failed write rejects and the toolbar says "not saved", as for a Query File.

Proposed on 2026-10-17 with [#1544](https://github.com/aidenlx/zotlit/issues/1544).

## Considered Options

- **A Query File in the vault** (rejected): the researcher did not make it, would see it in the file explorer, and could delete or rename it from under the view.
- **Workspace state of the leaf, as the sidebar Annotation View keeps its query** (rejected for the Library View): it is per leaf and goes when the leaf closes, but the Library View comes back as the researcher left it in every tab that opens it.
- **`app.saveLocalStorage`** (rejected): per device, and does not sync with the vault.
- **Plugin data through the SettingsService** (chosen): per vault, synced with the vault's plugin folder, validated by one schema, and its `flush()` reports a failed write.
- **Move the sidebar Annotation View to plugin data too** (rejected for now): its query is per leaf by design (ADR 0041 keeps its Follow Mode in workspace state the same way). It can save to its own plugin-data key later without a change to the contract.

## Consequences

- The document, not the Query View text, is what plugin data holds. A toolbar change that the document has no field for, such as a filter edit or a column width, does not stay; the Library View offers the controls whose state the document keeps.
- The SettingsService stores `library.document` as a plain JSON object and does not validate its shape; the Library View Document module is the one place that reads it, field by field: a stored value that is not an object takes the default document, and a field that does not parse takes its default, so one unknown field never resets the rest (amended after the #1543 review). The settings module therefore does not depend on the Library View.
- The Library View still runs every query through the database Read Mode (ADR 0047); saving the document never writes to Zotero.
- The host contract has two hooks for the Library View (#1545). `libraries` puts the selected Library on the request and in its run key, so a change of Library runs the query again; the host calls `contextChanged()` after it, since the text alone does not change. `displayOnly` removes every toolbar control whose change the document cannot keep: the view menu, Group, Filter, the row limit, the Properties menu, column resize and the property pages. Every control reads one capability set, `QueryView.can` (`views`, `group`, `filter`, `limit`, `properties`, `columnWidth`, `propertyPages`), that the host options decide; a new control that the document cannot keep adds a flag there, not a check of its own (#1547). The Library View is single-purpose, a familiar first look at the library: what is left is the result count, Sort and a "Save as query file" button. A researcher who wants the full Query View, with its Layouts, properties, filters and grouping, saves the list as a Query File and works there (amended after the second interface review).
- Every Library View query has a row limit of 1,000. On a 50,000-Item Stress Build, an unlimited My Library kept the window from responding for more than 30 s; with the limit it showed in 0.2–0.4 s, and the toolbar says "1000 of 50000 results". The limit applies after the sort, so a search with more matches than the limit loses the lowest-ranked ones (ADR 0073).
- "Save as query file" writes the Query View text of the document, minus the search key set, with the Library as a filter (ADR 0072) and the row limit kept, so the saved file shows what was on screen. The vault-side facets have no Query File form yet (#1531).
- A host can narrow the rows after the query with `rowPass` (`{key, keeps(indexedKey)}`), for the conditions the vault answers (ADR 0072). While a pass is active the view reads only the Indexed Key of every match, in the view's sort; the pass keeps some keys, the view's limit cuts the kept keys, and only that page is read with its fields, in the kept order, so "N of M results" counts kept rows. The pass key is part of the run key. The facets are document state, not a toolbar control, so `can` has no flag for them. On a 50,000-Item Stress Build this took Has note from 1.2–1.3 s (longest frame gap 124–141 ms) to 0.19–0.23 s (59–67 ms), and Unread from 1.2–1.4 s (203–226 ms) to 0.31–0.36 s (91–108 ms), the rest being the drawing of 1,000 rows. An engine condition (#1531) would remove the key-only read too.
- The Reading Card (#1552) is a second Query View inside the Library View, with no toolbar: one Annotations view filtered by `item == this.item`, whose Query Context is the selected Item, in that Item's Library. The list itself still binds no Query Context. The card shows every Annotation type, as the Annotated facet counts them, and takes its buttons from the row menu's operations (ADR 0074).
- The Library View Document module owns the document's transitions (select a node, set the facets, set the search, take a toolbar change) and every derivation from it: the list's request, the tree's paper and unread counts, the Libraries of a node, and the text "Save as query file" writes. The Library Tree, the search box, the Library View and storage all call it, so the tree's counts and the list cannot be built two ways (amended after the #1543 review). The document on screen is the one the module holds, never a re-read of plugin data while a save is queued.
- The host can name what left the list empty with `empty`, in place of the Query View's filter hint: a search that found nothing offers "Search all libraries", then clearing the search; facets that left nothing say so (#1543 review).
- The selection follows the rows on screen: a search, facet or node change that leaves the selected row out lets go of it, and the Reading Card hides. "Show in Library" reports whether the Item is listed; an Item past the row limit gets a notice naming the limit instead of a selection that does not show.
- When the Query Context or the Libraries of a run change, the Query View clears its rows while it reads, so rows bound to another Item or Library never show under the new binding; this holds for the Reading Card, a Library Tree node change and the sidebar alike. A host that names the Item its rows belong to may keep the last rows while the new binding reads, and change the name in the render that draws the new rows (amended when the sidebar Annotation View stopped flashing on a switch): the sidebar keeps the last Item, its name, attachments and cards, until the next Item's cards are read, or shows the next Item's name over its cards loading once the read has taken 150 ms. Rows still never show under another Item's name.
- A setting changed just before the plugin unloads still reaches the next instance: `SettingsService.release()` starts the last write as the plugin unloads, and the next instance waits for it before it loads plugin data. A change made after `release()`, such as a view that saves as it closes, is written at once and handed over the same way; writes run one at a time, so the last change that begins is the last to land. A write that begins after the next instance has read the handoff is not covered.
- The Reading Card offers two buttons, Open PDF and the Literature Note; Insert citation and the rest of the row menu sit under its More button, and "Open in the annotation view" is an icon button with the annotation view's highlighter icon (amended after the footage review: "Open in sidebar" did not say what it opens). The card is the item details, and one rule shows it at every pane width: while the researcher keeps the details on, they show the selected paper, and with no row selected they count, in the same room, the papers of the tree node and those that pass each Reading State facet, as the paper count reads them, over "Select a paper to see its details.", so the first click on a row moves nothing. Those counts read only while they show; for Recent they count the Library Scope it lists. A Details button at the end of the search row turns them on and off and looks pressed while they show; Space on the selected row, the card's close button and a drag of its edge past the minimum turn them on or off as well. A click, the arrow keys, Tab, a right click and "Show in Library" all select a row alone and never change whether the details show, so a click needs no wait and a double click always reaches the row and opens the PDF; Escape leaves the details as they are. Whether the details are off is part of the Library View Document, as `cardClosed`, so a reload keeps them off (amended after the details review: the card's earlier modes, shown for a click but not for the arrow keys over a narrow list, closed for a wide one, with a click that waited out a double click, were rules the researcher could not see). Beside a wide list the details sit after it; below 56rem of pane they sit under the tree and the list together, across the whole pane at half its height, and the list stays above them, with the selected row scrolled into view as they turn on. A card 42rem wide or more, at the bottom or dragged wide, sets the title page, the buttons and the abstract beside the info and the Annotations, in two columns. The researcher sets the card's width by dragging its inner edge, as a sidebar is resized, or with the arrow keys on that edge; a double click returns it to the default 24rem. The width is part of the Library View Document, as `cardWidth`, and is clamped on read and on each resize so the list keeps at least 20rem beside it (amended after the typography review). Under a narrow list the card has no resize edge, and the kept width waits for a wide pane; dragging its edge past the minimum width turns the details off, as an Obsidian sidebar collapses, and keeps the width it had before the drag.
- The Library Tree beside a wide list has a toggle at the start of the search row that collapses it, pressed while it shows, and an inner edge that sets its width as the card's does: a drag, the arrow keys, Home and End, a double click for the default 14rem, and a drag past its 10rem minimum collapses it. Both are part of the Library View Document, as `treeCollapsed` and `treeWidth`, read field by field like the card's. Below 36rem of pane the tree hides and its toggle shows it over the list, above the details, for a while, as before; collapsing it beside a wide list puts that away too (amended after the details review).
- The Library View Document dropped its Layout and Visible Properties (amended after the second interface review): no control writes them any more, and a stored `layout` or `order` from an earlier build is a field the module no longer reads, so it is ignored without resetting the rest.
- The Reading Card shows what Zotero's item pane holds, laid out like the title page of a paper for researchers who are not technical (amended after the second interface review and the card redesign; Zotero's dense label-and-value table and its stack of accordions are not copied). From the top: the Item type as a small kicker with its icon; the title in the serif face, one step above the body text rather than a display size, so a long title stays a few lines in a narrow card (amended after the typography review); the creators in full; the Venue in italics with volume, issue, pages and year; one row of quiet chips for the DOI as a link and the citation key with a copy button; then the buttons. Then the abstract, cut to a few lines with "Show more". Then the info: where the Item sits, as Library › Collection paths, its tags as chips, its files and its Zotero notes as short lists, the date added, and "All fields", which opens the other fields the Item has a value for. Last, "Your annotations": the count of each colour and the first two Annotations as short colour-ruled quotes with their page, then "See all N annotations", which mounts the Annotation Cards; the preview reads only those two. Sections are parted by thin rules and space, not boxes. A part with nothing in it is left out. The card never writes to Zotero, so it has no add buttons. Whether "All fields" and the full Annotations are open is remembered for the Library View, not per Item.
- The Library View Document also keeps where the researcher was in the tree, so reopening the tab or reloading Obsidian puts them back (amended after the persistence review): `expanded`, the keys of the Library Tree nodes left open. A node key the tree no longer has is dropped on read without resetting the rest; the tree still opens the ancestors of the selected node. The list's scroll position is not kept. The selected paper is session state, as ADR 0074 has it: a new tab opens with no paper selected, and the item details show what the list holds until the researcher selects one. A `selected` field an earlier build stored is ignored on read without resetting the rest (amended after the details review: a paper restored from the last session put the details on a paper the researcher had not asked for, and a list that restored one raced the selection a reveal made).
