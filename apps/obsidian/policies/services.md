# Services

The `zotlit-services` lint rules cover the mechanical part of the service architecture. The reviewer checks the rest:

- **Effect shape.** An Effect service's tag shape is Effect-native: its methods return `Effect`s, each method with arguments through `Effect.fn("<Tag>.<method>")`, or `Effect.fnUntraced` on a per-message or per-item hot path (`CODING_STANDARDS.md` → Effect; `effecttsgo/effect-fn-opportunity` checks it); a member with no arguments is an `Effect` value traced with `Effect.withSpan("<Tag>.<member>")` (`effecttsgo/lazy-effect` reports a zero-argument method), and state others watch is a `changes` Stream. Its layer is a `layer<Name>` export beside the tag (`layerUseLedger`), or a `layer<Name>(deps)` function when it takes plain inputs (`layerLogOutput(plugin)`).
- **Bridge.** Callers outside Effect — legacy services and views — hold the tag's service itself and the container's `bridge` (an `EffectBridge`, `@/lib/effect-bridge`). `build.ts` reads the service once, `useValue({ release: () => runtime.runSync(Release) })`; consumers type their deps as a `Pick<Release["Service"], …>` beside a `Pick<EffectBridge, …>`, and run each call through it: `bridge.runSync(…)`, `bridge.runPromise(…)`, `bridge.subscribe(stream, …)`. Nothing else calls `runtime.runSync` / `runtime.runPromise`, which fail or rebuild after unload: a callback that needs a service gets it read once at build. A call a caller fires and forgets (`void bridge.runPromise(…)`) cannot fail: the service handles its own failure, or the caller adds `catchCause` and logs. The bridge is the migration seam, not the target: a consumer that converts to Effect yields the tag and drops its `bridge` dep, until the bridge is left only where a callback from outside Effect (an Obsidian event, a React handler) enters it.
- **Edge handle.** Views and legacy callers that a later slice converts may hold an edge handle in place of the tag's service and the bridge: one object per tag that `build.ts` builds over the bridge (`bindQuery`, `bindItemLookup`). Each member runs one call through the bridge and maps its Exit to the caller's answer (`valueOr`); the handle holds no other logic. A member whose call has no released answer runs through `bridge.runPromise`, so the caller gets the value or the failure. A handle may also serve one Effect function over several tags (`bindBatchUpdate` for `runBatchUpdateAll`) until its caller converts. A handle may serve the Effect functions of one feature (`bindTemplateData` for the Template data reads) until its callers convert.
- **Plain adapter (backlog).** A `<service>/plain.ts` adapter (`plainZoteroReads`) runs each method on the runtime and returns values and Promises. The ones left retire into the bridge (#1710); write no new one. A `plain.ts` that only converts a service's dates to `Temporal` for plain code, and runs nothing (`zotero-local-api/plain.ts`), is the date edge (CODING_STANDARDS.md → Time), not an adapter.
- **Engine in a layer.** A state machine with concurrency of its own is Effect code in its layer: the Zotero Local API session (`zotero-local-api/session.ts`) keeps its state in `Ref`s, shares one request in flight between callers through a slot, as the Capability Probe does, queues work per key with a `Semaphore`, runs background work on the layer's Scope, bounds a request with `Effect.timeoutOrElse`, reads the `Clock`, and cancels by interruption rather than by `AbortSignal`. A large state machine that coordinates none of that may stay a plain class that the layer owns (`AnnotationRepositoryCore`): it publishes its events through a callback the layer turns into Streams, and reaches other services through `scopedBridge`, the bridge over the layer's own Scope. An engine core that holds the layer's bridge takes the tag service directly and runs its Effects through that bridge: `runSync` for a read, `runPromise` for a call, `subscribe` for a Stream. `AnnotationRepositoryCore` does this with `ZoteroLocalApi["Service"]`; no adapter sits between them.
- **Conversion scope.** A legacy service changes to Effect only in a change made for that conversion. The legacy list in `oxlint.config.ts` is the conversion backlog: the change takes the file off it, injects the service through `useValue`, and drops `ready` from its consumers' `Pick` deps and awaits.
- **Leaves first.** Convert a service once its dependencies are in the Layer graph. A legacy dependency enters the graph through `serviceLayer` when an Effect service first needs it, rather than through the container. `QueryClients` was bridged ahead of any Effect consumer, by decision; the Annotation Repository layer and the Excerpt Image display now yield it, so its bridge serves the legacy consumers that remain.
