# Services

The `zotlit-services` lint rules cover the mechanical part of the service architecture. The reviewer checks the rest:

- **Effect shape.** An Effect service's tag shape is Effect-native: its methods return `Effect`s, each method with arguments through `Effect.fn("<Tag>.<method>")`, or `Effect.fnUntraced` on a per-message or per-item hot path (`CODING_STANDARDS.md` → Effect; `effecttsgo/effect-fn-opportunity` checks it); a member with no arguments is an `Effect` value traced with `Effect.withSpan("<Tag>.<member>")` (`effecttsgo/lazy-effect` reports a zero-argument method), and state others watch is a `changes` Stream. Its layer is a `layer<Name>` export beside the tag (`layerUseLedger`), or a `layer<Name>(deps)` function when it takes plain inputs (`layerLogOutput(plugin)`).
- **Bridge.** Callers outside Effect — the plugin shell and views — hold the tag's service itself and the plugin runtime's `bridge` (an `EffectBridge`, `@/lib/effect-bridge`). `createPluginRuntime` (`plugin-runtime.ts`) reads the service once, `release: runtime.runSync(Release)`; consumers type their deps as a `Pick<Release["Service"], …>` beside a `Pick<EffectBridge, …>`, and run each call through it: `bridge.runSync(…)`, `bridge.runPromise(…)`, `bridge.subscribe(stream, …)`; a module whose Effect body plain code runs receives `{ context, bridge }`, the `Context` of every tag that body `yield*`s, with plain values such as the `App` beside them (`PandocExportDeps`), and a `*Deps` bag of services takes this shape when work touches its module; [Unload](unload.md) gives what unload does to each run and how its caller answers. Nothing else calls `runtime.runSync` / `runtime.runPromise`, which fail or rebuild after unload: a callback that needs a service gets it read once at build. Each edge shape has one helper: an Effect calls a legacy Promise port through `portCall` (`lib/legacy-port.ts`), whose `LegacyPortError` keeps the rejection as its cause, and a modal callback runs on a runner built over the bridge with `Effect.provideContext` (`runBatchWith`, `services/batch-run.ts`). The bridge is the migration seam, not the target: a consumer that converts to Effect yields the tag and drops its `bridge` dep, until the bridge is left only where a callback from outside Effect (an Obsidian event, a React handler) enters it.
- **Edge handle.** Views and legacy callers that a later slice converts may hold an edge handle in place of the tag's service and the bridge: one object per tag that `plugin-runtime.ts` builds over the bridge (`bindQuery`, `bindItemLookup`). Each member runs one call through the bridge and maps its Exit to the caller's answer (`valueOr`); the handle holds no other logic. A member whose call has no released answer runs through `bridge.runPromise`, so the caller gets the value or the failure. A new handle has a test that it resolves with the result and, after unload, settles as the bridge does. A handle may also serve Effect functions over several tags (`bindNoteActions` for the note commands and menu entries) until its callers convert. A handle may serve the Effect functions of one feature (`bindTemplateData` for the Template data reads) until its callers convert.
- **Views.** A view reads Effect services through view atoms in the plugin's view registry (`@/lib/view-atoms`), keeps its own state in a per-leaf model with pure transitions, and runs its gestures as commands ([ADR 0082](../docs/adr/0082-obsidian-views-read-effect-services-through-view-atoms.md)). Its pattern catalogue and pitfalls are in the ADR; a view that converts drops its store and its `bridge.subscribe` calls.
- **One contract per service.** Every caller reads the service's tag: Effect code `yield*`s it, and code outside Effect uses the bridge above (`zotlit-services/no-plain-service-adapters`, `scripts/oxlint-plugin-services.ts`).
- **Engine in a layer.** A state machine with concurrency of its own is Effect code in its layer: the Zotero Local API session (`zotero-local-api/session.ts`) keeps its state in `Ref`s, shares one request in flight between callers through a slot, as the Capability Probe does, and a caller that joins it retries when it ends interrupt-only, so each caller ends only on its own interrupt; it queues work per key with a `Semaphore`, runs background work on the layer's Scope, a notice or deferred announcement included, as a fiber on the layer's `FiberSet` (`Effect.yieldNow` first when the order matters), with state in `Ref`s rather than in closures that call a runner, bounds a request with `Effect.timeoutOrElse`, reads the `Clock`, and cancels by interruption rather than by `AbortSignal`. A large state machine that coordinates none of that is Effect functions over one state record that its layer builds: the Annotation Repository core (`annotation-repository/core/`) takes the `CoreState` as its first parameter, `yield*`s the services the record holds (`ZoteroLocalApi["Service"]`, `ZoteroReads["Service"]`, `QueryClients["Service"]`), and publishes its events through a callback the layer turns into Streams. The layer's members `yield*` the core functions. Callbacks that a library calls (TanStack Query read and mutation functions) and the `Disposable` that `hold` answers are its edges, and run through `scopedBridge`, the bridge over the layer's own Scope.
- **Effect services only.** Every plugin service is an Effect service: a tag and a layer in `pluginLayer`, which `plugin-runtime.ts` composes into the plugin's runtime. `zotlit-services/no-legacy-service` rejects a class that extends `Service`.
