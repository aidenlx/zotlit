# A Literature Note Profile is its document

Spec #865 shipped a Literature Note Profile in two homes: a settings record in `data.json` (ID, label, a pointer to the document, five sparse bindings) and the Literature Note Template document it pointed at (body, blocks, filename rule, Managed Frontmatter, and a dead `profileDefaults` suggestion of folder and citation style). The #913 sharing prototype made the cost concrete: a Profile cannot be sent as one thing, and two vaults holding the same document have nothing that says it is the same Profile. Decided in #916 on map #835, before the record format shipped to any user — `main` is still at settings version 9 — so correctness and simplicity won over compatibility.

**The Profile is the document.** Every `zotlit-profile.<slug>.md` in the template folder is a Literature Note Profile; nothing registers, points at, or installs one, and a file that arrives by any route (paste, sync, git, drag) is a Profile the moment it is there. The manifest carries the Profile ID (`id`, the same twelve-character Nano ID as before, minted at creation and never authored), the label (`name`), and the five bindings as flat top-level keys (`folder`, `citationStyle`, `importFolder`, `importColoredHighlights`, `importAnnotationsAsTemplate`); `profileDefaults` is removed. The filename is `zotlit-profile.` plus the normalized label, with the ID appended only on collision, and it carries no identity: renaming keeps the Profile, dropping the prefix removes it from the registry. A duplicated Profile is a file copy that mints a fresh ID; a file that arrives with an ID the vault already holds is a second edition of that Profile, never a new one. Two labels may repeat — the ID disambiguates — but a file whose manifest fails validation, or either file of a colliding ID pair, is not a Profile: it is excluded from the registry and diagnosed in place, and its notes hit the unknown-Profile backstop, on the same principle as an unknown stamp — an ID ZotLit cannot trust is not resolved.

**The default Profile is the one settings record.** Its total bindings stay in `data.json` as the settings a new user expects to find in the settings tab; its look is the built-in template until the user ejects `zotlit-profile.default.md`, whose manifest carries the reserved `id: default` and no bindings (bindings there are a validation error). Existence of that file *is* the ejected state — `data.json` keeps no document pointer at all. ADR 0027's sparse-over-total-root inheritance is unchanged; only the root's home is named. A sender is expected to leave folder keys unset so a shared file lands notes in the recipient's default folders, and the import preview shows folder and style as editable before anything is written.

**The file is the editor.** The settings tab keeps the Profile list, the default Profile's binding rows, and Open / Duplicate / Delete actions; editing any other Profile means editing its file, in keeping with ADR 0017's line that vault files stay user- and agent-edited. A new `ProfileService` is the registry — fed by `TemplateService`'s document events filtered on the prefix, owning Profile resolution, create, duplicate, and delete-as-move, and exposing a `ready` promise every resolution awaits so a note operation that runs before the folder scan completes cannot misreport a Profile as unknown. The Pack install/revert service and its `note.template-pack-installs` records are deleted; the partial-bundling export survives as a pure function for the sharing prototype to reuse or drop.

## Considered options

- **Keep the two homes, handle sharing and sync at the import seam** (#913's prototype): changes no format, but manages the symptoms and leaves two identically labelled rows that nothing can tell apart.
- **A per-vault override layer over the file** for the recipient-owned folder keys: re-creates the scatter it would fix; sparse-by-default sharing makes the format itself carry "the folder is the recipient's".
- **The default Profile as a file too, written on first load**: one model for every Profile, but a plugin-created file every user gets and a settings tab that edits YAML — rejected while the settings tab is the new user's door.

## Consequences

- The v9→v10 settings migration and the legacy converter (#903's read-only window and prompted one-shot conversion are untouched) target the file format directly; the converter writes `zotlit-profile.default.md`. `note.profiles`, `note.template-pack-installs`, and the default's `document` pointer are removed rather than migrated; dev and Fixture vaults are rebuilt.
- In-vault overwrites bypass the refuse-on-user-edit gate the Pack service had; the second-edition consequences dialog at the import seam is the remaining guard, and #913 decides what that seam is.
- ADR 0025 is amended (the manifest holds the bindings, not defaults; the envelope install lifecycle is gone), ADR 0027 is amended (the root's home is named; a documentless Profile exists only as the default), and ADR 0030's ID-only document filename is superseded by the slug filename.
- #914's create dialog writes a file; duplicate is a file copy; "duplicating Default is where a document first hits disk" dissolves — every non-default Profile is a file from birth. The Workbench keeps inspect commands for Profiles; an agent edits the file directly.
