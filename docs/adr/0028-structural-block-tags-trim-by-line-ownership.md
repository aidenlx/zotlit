# Structural block tags trim by line ownership

> **Amended by [ADR 0035](0035-profile-annotation-section.md).** Line ownership applies to Managed Block tags. The Annotation Section uses a fixed document header and preserves surrounding source bytes.

ADR 0025 and ADR 0027 gave the Literature Note Template document two structural block tags — `{% managed %}` … `{% endmanaged %}` and `{% annotation %}` … `{% endannotation %}` — and ADR 0027 states that the Annotation Block "contributes nothing to the note body". The implementation made that claim false in a whitespace-shaped way: block ranges were sliced byte-exactly, so a block written on its own lines left a blank line where it stood, and the Annotation Block's own newline entered every drag-insert. Generated documents therefore glued the tags to their contents (`{% managed %}{% if … %}`), which renders correctly and reads badly.

**A structural tag that owns its line contributes no bytes.** A tag is *line-owning* when only whitespace stands between the line start and the tag and a newline follows it directly; then its indentation and its trailing newline belong to the tag and are removed on extraction and on stripping. A tag written inline keeps every surrounding byte, so an inline block behaves exactly as it did before. A block owns exactly its own lines and never a neighbour's blank line; the created note body is normalized once, at the end of create-time rendering, to a single trailing line break, which is what finally makes ADR 0027's claim true wherever the author puts the block.

**Removal and replacement own the line differently.** The Annotation Block is removed, so it takes its whole line with it. The Managed Block is *replaced* by the Managed Region, so the line break its close tag owns is put back after the region — otherwise the region's last line would run into the text below it. This is not a special case for one block but the same rule read correctly: the tag's line break terminates the line the replacement now occupies. It also carries the backward compatibility, because a pre-rule glued document already has a line-owning close tag whenever the `content` slot source ends with a newline.

**Automatic trimming, not whitespace-control markers.** The obvious alternative was to let authors write `{%- managed -%}`, matching LiquidJS's `-%}` and Eta's `<%_`. It cannot work: these four tags are not engine tags. They are exact-literal `indexOf` matches over the raw document body, sliced before Liquid or Eta ever sees the text, which is what makes them language-agnostic across both engines and what lets an Eta document carry Liquid-shaped tags. A marker on a tag the engine never parses would have to be implemented twice over anyway, and would then contradict the automatic rule. The tags keep exactly one spelling; engine whitespace control (`greedy: false` for Liquid, `autoTrim: [false, false]` for Eta) is untouched, so authors keep full control of their own logic tags.

`formatManagedRegion`'s `.trim()` stays. It answers a different question — the note-side contract that `%%zt-managed%%` markers each sit alone on their line, so the region stays re-detectable and create-time and update-time bytes match regardless of author layout (ADR 0025's round-trip guarantee). The line rule governs the document; the trim governs the note.

Consequences: `synthesizeLegacyLiteratureNoteTemplate` emits the line-owning layout at all three production entry points (converter, Customize seed, Pack install), and #865's byte-identical conversion bar survives. One exception is written into the generator: an indented content insertion keeps its glued open tag, because a line-owning open tag would take the author's indentation with it and lose those bytes. A nested Annotation Block is removed by the same line rule, so it leaves no interior blank line of its own; blank lines the author left around it are theirs and stay. Decided in the #880 grilling; no shipped default Profile document exists yet, so the deferred default-Profile-document work inherits this layout.
