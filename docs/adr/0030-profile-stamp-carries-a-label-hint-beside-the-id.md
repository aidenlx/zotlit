# The Profile stamp carries a label hint beside the ID

ADR 0025 and ADR 0027 record a note's Literature Note Profile in the `zotlit-profile` system frontmatter stamp, and the stamp held only the Profile ID — an opaque 12-character Nano ID. A person reading the note as plain text, in Obsidian's Properties pane or in any editor, cannot tell which Profile `V1StGXR8Z5jd` is, and the one place that could tell them (the settings tab) is exactly where they are not looking.

**The stamp is `<label> (<id>)`; the ID is the only authority.** ZotLit writes the Profile's current label, a space, and the Profile ID in parentheses. It reads the stamp with an end-anchored match on `(<12 ID characters>)` and resolves membership by exact ID equality alone. The label part is a *Profile hint*: it is informational, never compared, never used as a fallback when the ID is unknown (an unknown ID stays the `unknown-literature-note-profile` diagnostic, in keeping with "membership is never inferred"), and a hint that no longer matches the Profile's label changes nothing. A bare-ID stamp remains valid. Every ZotLit write of a stamped note re-emits the stamp with the current label, so a renamed Profile's hint self-heals on the next managed update and stale hints only survive in notes ZotLit never touches again. The hint is the trimmed label with no other transformation — no slug rules, no character constraints.

**Considered forms.** `slug--id` needs slug rules for every script ZotLit's users write in, and a slug is lossy: the label no longer reads back as the user wrote it. `id label` parses trivially but puts the opaque part first, which is the readability problem restated. A YAML mapping `{ id, label }` is the cleanest structure, but Obsidian's Properties UI does not edit nested objects and every stamp reader would change shape. `label (id)` keeps the label lossless, parses from the end so a label ending in `)` is safe, and matches how the Profile picker already presents a Profile (#904: label first, ID secondary).

**Scope.** The hint lives in note frontmatter only. The `&profile=` parameter of the Companion URL keeps carrying the bare Profile ID, and the Profile document filename (`literature-note-<id>.md`) and command id stay ID-only; a readable document filename is a file rename with link consequences and gets its own decision. The ID's length and alphabet are the ones the refactor that replaced UUIDs settled: twelve Nano ID characters from `A`–`Z`, `a`–`z`, and `0`–`9`. Decided in the #835 follow-up grilling, before any Profile stamp shipped to users.
