# Item Query shares execution between collection and incremental delivery

> Amended 2026-10-10 by ADR 0071: the operations take one of three Query Datasets, `ITEMS`, `ATTACHMENTS`, and `ANNOTATIONS`, and Relation Lists are hydrated only when a request names them.

> Amended 2026-10-10: the operations take a Query Dataset. `@zotlit/item-query` exposes `collectQuery(dataset, request)`, `consumeQuery(dataset, request, begin)`, and `describeQueryCustomFields(dataset)`, with the descriptor values `ITEMS` and `ANNOTATIONS`; `queryItems`, `consumeQueryItems`, and `describeItemQueryCustomFields` are their Item forms under the old names. The descriptor carries every fact that differs between the two datasets (names, defaults, Sortable Fields, filter registry, hydration), so the request planner, the diagnoser, the schema description, and the Obsidian adapter branch on no dataset flag. The Attachment-file resolver of an Annotation Query arrives as an Effect reference, on the pattern of the tuning service. The shared execution path, the database and clock services, and the cancellation and delivery rules below are unchanged.

`@zotlit/item-query` exposes `queryItems`, `consumeQueryItems`, and `describeItemQueryCustomFields`, each returning an Effect (Effect v4). The query operations share one execution path that hides parsing, validation, planning, candidate narrowing, hydration, evaluation, sorting, projection, cancellation, and truncation behind one interface. The build-only `@zotlit/item-query/schema` entry generates the static Item Query Schema from the same registries that execution uses; `describeItemQueryCustomFields` reads the active source's custom-field capabilities. Compilation stages, evaluator values, planner tuning, and relation loading remain implementation details.

The database arrives as a service from `@zotlit/db`, which owns every SQL statement as Effect-native readers over the borrowed `NodeDatabaseClient`; `@zotlit/item-query` contains no SQL. Zotero SQLite is a local-substitutable dependency, so tests cross the same readers on a Zotero-made database. The Query Clock also arrives as services: the Effect `Clock` and an Item Query time-zone reference. The Obsidian adapter is the only Promise edge: `ItemQueryService` runs each Query Job as a fiber and maps Obsidian's `AbortSignal` to fiber interruption at that one `runPromise`; the worker runs the job on the time-budget scheduler as a fiber in the ZoteroReads handler, and `CancelItemQuery` interrupts that fiber. ZoteroReads owns the connection scope and supplies the borrowed client and captured identity directly. The Obsidian adapter owns the resolution of the Target Libraries, CLI decoding, its 100-row default, Temporal wire serialization, and the versioned envelope, and it runs each operation on the time-budget scheduler that the package exports.

A successful Query Result includes the normalized Item Query, Query Rows, `returnedCount`, and `truncated`. Projection values use one recursive `ProjectionValue` type. An invalid request fails with one typed `ItemQueryError` carrying a stable code, location, message, and recovery hint. An unsupported database layout and a database failure are separate typed failures, cancellation is fiber interruption, and an implementation failure is a defect. Every sort runs in memory, so the public sort contract does not depend on SQL ordering.

The Obsidian query adapter runs queries, schema reads, projection, and JSON encoding in the ZoteroReads Web Worker of ADR 0068. The worker borrows its current connection for each query and releases it after execution and file closure. Two query slots bound retained query memory while other ZoteroReads operations keep serving. Query Rows and Temporal values remain in the worker; only bounded JSON answers and export receipts reach the renderer.

Each request has an internal job id. `CancelItemQuery` interrupts that job, including a query waiting for a slot. The original request settles after the writer closes and the connection borrow ends. The renderer then removes the staged file and releases the caller's id. The Query Job of the worker closes the staging writer in its scope before RPC settles; `ItemQueryService` publishes and removes the staging file. The encoder only writes chunks. A successful export closes its staged file before the renderer publishes it without replacing an existing destination. Cancellation before publication removes the staged file; successful publication wins a concurrent cancel. Plugin disposal cancels and drains query jobs before ZoteroReads disposal. Worker failure and recovery follow ZoteroReads.

Cooperative scheduling alone cannot bound renderer garbage-collection pauses, and transferring a complete large JSON string back into the renderer can itself block the interface. Worker isolation and bounded replies address both causes. Responsiveness measurement checks renderer timer gaps throughout the worker call, including result transfer and file publication. Execution slices and encoding steps retain the spec's 16 ms p99 and 32 ms maximum limits in the worker; renderer gaps are an additional check against those limits. Total-time and cancellation budgets still apply.

Cancellation is cooperative at the engine's scheduler yields and file writes. A hung worker follows the shared ZoteroReads heartbeat and recovery path; a query does not terminate the worker used by the other readers. Measurement aggregates statement events and heap samples in the worker before returning compact diagnostics to the renderer.

`consumeQueryItems` starts a consumer after ordering establishes the normalized request, count, and truncation. It hydrates and projects one chunk, awaits the consumer write, and then proceeds. A successful end returns the consumer's value; consumer failure or interruption stops further reads. `queryItems` collects these same chunks into the complete Query Result. The CLI encodes them directly into bounded inline text or an unpublished file, so an export retains one projected chunk rather than every projected value. Unlimited ordering still retains the compact matches and sort keys.
