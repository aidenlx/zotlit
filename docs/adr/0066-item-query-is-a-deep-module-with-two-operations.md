# Item Query is a deep module with two operations

`@zotlit/item-query` exposes two operations, `queryItems` and `describeItemQuery`, and each returns an Effect (Effect v4). The first operation hides parsing, validation, planning, candidate narrowing, hydration, evaluation, sorting, projection, cancellation, and truncation behind one interface. The second returns the Item Query Schema from the same registries that execution uses. Compilation stages, evaluator values, planner tuning, and relation loading remain implementation details.

The database arrives as a service from `@zotlit/db`, which owns every SQL statement as Effect-native readers over the leased `NodeDatabaseClient`; `@zotlit/item-query` contains no SQL. Zotero SQLite is a local-substitutable dependency, so tests cross the same readers on a Zotero-made database. The Query Clock also arrives as services: the Effect `Clock` and an Item Query time-zone reference. The Obsidian adapter is the only Promise edge. It owns source leases, Target Library resolution, CLI decoding, its 100-row default, Temporal wire serialization, and the versioned envelope, and it runs each operation with an `AbortSignal` and the time-budget scheduler that the package exports.

A successful Query Result includes the normalized Item Query, Query Rows, `returnedCount`, and `truncated`. Projection values use one recursive `ProjectionValue` type. An invalid request fails with one typed `ItemQueryError` carrying a stable code, location, message, and recovery hint. An unsupported database layout and a database failure are separate typed failures, cancellation is fiber interruption, and an implementation failure is a defect. Every sort runs in memory, so the public sort contract does not depend on SQL ordering.
