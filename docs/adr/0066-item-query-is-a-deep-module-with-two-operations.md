# Item Query shares execution between collection and incremental delivery

`@zotlit/item-query` exposes `queryItems`, `consumeQueryItems`, and `describeItemQuery`, each returning an Effect (Effect v4). The query operations share one execution path that hides parsing, validation, planning, candidate narrowing, hydration, evaluation, sorting, projection, cancellation, and truncation behind one interface. `describeItemQuery` returns the Item Query Schema from the same registries that execution uses. Compilation stages, evaluator values, planner tuning, and relation loading remain implementation details.

The database arrives as a service from `@zotlit/db`, which owns every SQL statement as Effect-native readers over the leased `NodeDatabaseClient`; `@zotlit/item-query` contains no SQL. Zotero SQLite is a local-substitutable dependency, so tests cross the same readers on a Zotero-made database. The Query Clock also arrives as services: the Effect `Clock` and an Item Query time-zone reference. The Obsidian adapter is the only Promise edge. It owns source leases, the resolution of the Target Libraries, CLI decoding, its 100-row default, Temporal wire serialization, and the versioned envelope, and it runs each operation with an `AbortSignal` and the time-budget scheduler that the package exports.

A successful Query Result includes the normalized Item Query, Query Rows, `returnedCount`, and `truncated`. Projection values use one recursive `ProjectionValue` type. An invalid request fails with one typed `ItemQueryError` carrying a stable code, location, message, and recovery hint. An unsupported database layout and a database failure are separate typed failures, cancellation is fiber interruption, and an implementation failure is a defect. Every sort runs in memory, so the public sort contract does not depend on SQL ordering.

The Obsidian query adapter runs each query, projection, and JSON encoding in an Electron utility process. Two warm processes bound concurrency. The parent pins the database read and its captured source identity until the worker closes its connection. Cancellation has two receipts: acceptance when the worker requests Effect interruption, and completion after its files and SQLite connection close. The parent stops a worker that does not accept cancellation within one scheduler slice, or has not closed its resources by the original request's 50 ms deadline. A closure receipt or confirmed exit releases the job; a stopped process remains unavailable until exit even if a late closure receipt arrives first. File exports write an unpublished file beside the destination, then the parent publishes it and removes the temporary name. Plugin disposal drains jobs and process exits before database disposal. Process logs return through the configured renderer logger.

Cooperative scheduling alone cannot bound renderer garbage-collection pauses, and transferring a complete large JSON string back into the renderer can itself block the interface. Worker isolation and bounded replies address both causes. Responsiveness measurement checks renderer timer gaps throughout the worker call, including result transfer and file publication. Execution slices and encoding steps retain the spec's 16 ms p99 and 32 ms maximum limits in either process; renderer gaps are an additional check against those limits. Total-time and cancellation budgets still apply.

Process isolation gives cancellation an operating-system stop boundary. A Node worker thread can stop executing while its termination still waits for a large isolate to be destroyed; measured cancellation exceeded 50 ms. The renderer caches its owned process ID and sends an operating-system stop signal directly, then waits for exit. Removing the unpublished file name starts in parallel with the stop; a final cleanup after exit covers a file-creation race. Its entry code is embedded in the plugin, materialized in an owned temporary directory, and removed after process exit. Each process checks that its owning vault renderer remains alive. Measurement aggregates statement events and heap samples inside the process before returning compact diagnostics to the renderer.

`consumeQueryItems` starts a consumer after ordering establishes the normalized request, count, and truncation. It hydrates and projects one chunk, awaits the consumer write, and then proceeds. A successful end returns the consumer's value; consumer failure or interruption stops further reads. `queryItems` collects these same chunks into the complete Query Result. The CLI encodes them directly into bounded inline text or an unpublished file, so an export retains one projected chunk rather than every projected value. Unlimited ordering still retains the compact matches and sort keys.
