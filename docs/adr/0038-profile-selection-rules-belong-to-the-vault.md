# Profile selection rules belong to the vault

The [Profile selection spec](https://github.com/aidenlx/zotlit/issues/918) chose an informed picker for new Literature Notes and excluded automatic rules. The automatic-selection grilling on 2026-09-06 reopens that boundary: users configure Profile Selection Rules once and create new Literature Notes under the Profile selected by those rules. The accepted [Automatic Profile Selection spec](https://github.com/aidenlx/zotlit/issues/971) and its child tickets record the implementation scope.

**The vault owns the rules.** Profile Selection Rules live in one ordered list in plugin settings for the vault. Each rule selects one Profile by its stable Profile ID, or Default. Initial conditions cover Collection membership, built-in Zotero Item type, Library scope, and exact Tag membership. Profile documents retain their identity, bindings, and template under [ADR 0031](0031-a-literature-note-profile-is-its-document.md). Keeping selection rules in vault settings gives the user one place to inspect them and keeps references to the user's Collections separate from a shared Profile document. Sharing or importing a Profile preserves this boundary.

**Conditions use ZotLit Filter Expressions in an explicit `and` / `or` tree.** Reuse the syntax and matching semantics adopted by Item Query, including Boolean operators, grouping, and negation, inside each condition. Store the conditions as a Rule Filter: a recursive `and` / `or` tree in the shape of an Obsidian Bases `filters` block, whose leaves are Filter Expressions. The tree is the ordinary way to combine conditions; `!`, `&&`, and `||` remain available inside a leaf. (Amended 2026-09-06 from one Filter Expression per rule.) Library is a separate scope, following Item Query's `personal` and `group:<groupID>` vocabulary. The source contracts are `packages/filter-expression/CONTEXT.md` and `docs/adr/0021-item-query-has-a-field-oriented-contract.md` on `feat/zotero-db-query-cli` at `b1c6789ed83c122f21fa533d08cca099d285bd36`. Port the existing parser and its tests; implement the required matching support against those contracts. The source branch's Item Query package currently holds its context contract. The four initial condition types remain the scope for Profile rules, and stable Collection references and descendant membership belong to the shared condition contract.

**The simple GUI is the primary editor.** Academic users choose Libraries, Collections, Item types, Tags, and a target Profile through labeled controls. The editor starts with a flat "Match all" group and offers "Match any", "Add group", and plain exclusion operators such as "is not". The GUI mirrors the Rule Filter tree: groups are its `and` / `or` nodes and each leaf is one row. A labelled row writes its canonical Filter Expression; an expression row edits the leaf as text. A leaf that the labelled rows cannot represent, including one that combines tests with Boolean operators, stays intact in an expression row.

**Library scope is visible and references are stable.** A rule starts with an explicit "All libraries" scope and can restrict that scope to selected Libraries. Collection choices show their Library and path. Persisted references use the personal-Library marker or group ID, together with the Collection key; names and paths provide display text. A Collection rename preserves the rule's reference.

**Membership conditions are explicit.** Collection conditions include subcollections by default and offer an option for direct membership only. Matching uses the Item's actual memberships across Collections, independently of the Collection selected in a UI. Tag conditions match exact, case-sensitive names and include both manual and automatic Tag applications.

**User order resolves overlapping rules.** The first matching rule selects the Profile, and the creation surface identifies that rule. Users place specific rules above broad rules. A manual choice for the current operation takes precedence over a Profile explicitly supplied by a command or Companion link, which takes precedence over the rule result. Default is the final fallback.

**A resolved selection creates directly.** Quick Switch and batch screens show the selected Profile, reason, and destination before creation and offer an override. Citation and Companion links create immediately when a matching rule or an explicit valid Profile selects the target, then show the resulting Profile and path. An Item with neither a matching rule nor an explicit Profile uses the picker with Default preselected. With only Default available, ordinary unmatched creation uses Default directly. This amends the earlier requirement to open the Profile picker for every new Literature Note when additional Profiles exist.

**Broken rules require an explicit choice.** Within the Item's Library scope, an applicable rule that cannot be evaluated stops automatic selection and reports the problem. A matching rule whose target Profile is unavailable does the same. The user chooses a Profile for the affected Item; a valid non-match advances to the next rule. An invalid explicit Profile selector also retains explicit recovery. Unaffected batch Items keep their automatic selections. Invalid configuration and an ordinary non-match remain distinct, including when Default is the only available Profile.

**The preview fixes the current selection.** Changes to Tags, Collection membership, or rules after a creation preview leave that operation's shown Profile and destination in place. Later operations use the changed conditions. If the selected Profile becomes unavailable, stop the affected creation and request another choice.

**Selection is explicit for the current operation.** A manual choice applies to that operation. Later operations select from their own explicit inputs, configured rules, and Default; previous creation choices contribute no selection source. The saved last-used Profile and creation-time memory writes are retired. This replaces the remembered-selection behavior introduced in [#919](https://github.com/aidenlx/zotlit/issues/919), so creating one note cannot change the preselection for another Item.

**Selection establishes new membership.** Rules apply when creating a Literature Note. Existing notes retain their recorded Profile membership as Item conditions change; unstamped notes retain Default membership, and unknown stamps retain diagnostics and explicit recovery. The Switch Profile action remains the way to change existing membership. Imported Notes retain their established stamp and operation-based Profile behavior. This preserves the one-Literature-Note-per-Item model and makes changes in Zotero organization independent of changes to existing notes.

**Batches select per Item.** Each new Literature Note receives its own rule result. One fallback choice applies to the unmatched Items and preserves the matched Items' selections. A separate, explicit action can use one Profile for every new Literature Note in the batch. Existing notes retain their recorded Profiles.

**Profile deletion warns about rule references.** The deletion dialog lists the affected rules and warns that the user must update them manually, including when the Profile has no stamped notes. Deletion can finish after this warning. Rules retain their original targets after deletion; the replacement Profile chosen for existing notes applies to those notes alone. The user repairs or removes the affected rules manually. External Profile document removal also leaves rule references in place, and both cases follow the broken-rule behavior above.
