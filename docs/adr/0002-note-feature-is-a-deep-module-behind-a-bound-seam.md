# Note-feature is a deep module behind a bound seam

The note feature exposes one small surface: `createNoteFeature(deps)` binds the operations to their collaborators once (in `build.ts`) and returns a `NoteFeature` object — `ready` plus `createNote`, `updateNote`, `overwriteNote`, `writeNoteUpdate`, `renderCitation`, `renderAnnotation`. Consumers hold that object (or a `Pick` of it, e.g. `Pick<NoteFeature, "renderCitation">` for a view that only cites) and never see the eight collaborators behind it.

The operations stay free functions internally — the factory captures `deps` in a closure and each method forwards to its function. The bound object is interface packaging, not a new layer; the batch runners still drive the same functions to fetch tags and paths once per run and reuse them.

Dependencies enter through `NoteFeatureDeps`, whose every member is a structural `Pick` of a full service sized to exactly what the operations touch (`db: Pick<DatabaseService, "acquireRead" | "state" | "client">`, and so on). Because the narrowing is structural, `createNoteFeature` accepts the real services with no adapter code, and tests hand-write literal stubs with no casts.

We previously passed a wide `NoteFeatureContext` DTO to the free functions at every call site. We replaced it because:

- **One DTO, five slicing views.** The context was consumed at ~12 sites and re-sliced five ways — two `Omit<…, "db">` shapes, two different `Pick`s, and a separately re-injected synchronous `db` view for the dragstart render path. The DTO's breadth was the union of every collaborator any operation touched, so every consumer imported far more than it used.
- **Cast-heavy tests.** Exercising a single operation meant constructing the whole surface; the operation test paid ~10 `as unknown as` casts to reach one path. Narrowed members let the test build a plain `NoteFeatureDeps` literal — casts dropped to zero.
- **Leaked collaborators.** View and service consumers threaded the full bundle through just to forward one method. Holding a `NoteFeature` (or a one-method `Pick`) confines the collaborators to `build.ts`.

We considered making note-feature a `Service` class. We rejected it: the feature owns no lifecycle or mutable state — compiled template artifacts live in `TemplateService`, and the DB lease is acquired per operation — so a class would add `super()`/disposal ceremony around a stateless closure. We also considered adapter objects at each call site to satisfy the narrowed members; structural `Pick` makes adapters unnecessary, since the full service already conforms.

## Consequences

- `NoteFeatureDeps` members are structural `Pick`s. Widening an operation to touch a new method of an existing collaborator means widening its `Pick` — a compile error at the seam, not a silent new coupling.
- Batch runners await `noteFeature.ready` (templates **and** the note index) before a `writeNoteUpdate` loop, where they previously awaited only `template.ready`. Strictly more correct — the loop assumes an indexed vault — and harmless, since that path already gates `noteIndex.whenIndexed()` upstream.
- `ensureFolder` / `ensureParentFolder` take a narrowed `FolderVaultApp` (a vault subset) instead of the full `App`, so the narrowed `deps.app` flows through unchanged.
- Two hitchhikers surfaced: `batch-import` and the note-feature actions reached collaborators through the old bundle (`noteFeatures.app`, `noteFeatures.template.ready`). They now hold their own `app` and `template` deps, and `NoteImportContext` no longer carries `noteFeatures`.
- The narrowing rippled one level further: `renderAnnotation`'s `zoteroPref: ZoteroPrefService` narrowed to `Pick<ZoteroPrefService, "dataDir" | "baseAttachmentPath">` in `NoteFeatureDeps`, so `buildAnnotationResolvers`/`renderAnnotations` in `lib/annotation-render.ts` — the shared helper both `renderAnnotation` and the dragstart render path call — took the same narrowed `Pick` to keep passing `ctx.zoteroPref` through unchanged.
- **Note-import then converged to the same seam.** `batch-import` packages its three runners (`runBatchImport`, `runChildImportByKey`, `reimportNoteByKey`) behind `createBatchImport(deps): BatchImport`, with the runners staying free functions internally. `NoteImportContext` became `NoteImportDeps` with every member a structural `Pick`, and the UI left the deps entirely: the classify/confirm modals now sit behind a narrow `NoteImportView` port (`openBatchModal` + `confirm`), built from the `App` in `build.ts` via `createNoteImportView`, so the runners hold no `App` at all. Consumers hold the bound object or a `Pick` of it: `protocol/register.ts` no longer extends the DTO and drops its `template`/`noteImport` wiring, and `actions.ts` holds `Pick<BatchImport, "runChildImportByKey" | "reimportNoteByKey">`. The note-import writer itself followed last: `NoteImportService` (a `Service<void>` class with `ready = Promise.resolve()`, no disposal, and no mutable state) became `createNoteImporter(deps): NoteImporter`, registered via `useValue` instead of `use`. Its `App` narrowed to an `ImportVaultApp` vault+`fileManager` subset, and the class methods became module-level free functions. The batch test builds a typed `NoteImportDeps` literal over a real in-memory client with a plain `view` stub, dropping the whole-object cast to zero.
