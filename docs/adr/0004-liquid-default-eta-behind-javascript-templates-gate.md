# Liquid is the default template language; Eta lives behind the JavaScript Templates gate

Templates are shareable vault content, and under Eta every template is a full-privilege script (`new Function` at compile time) — the pattern Obsidian's scorecard flags as "dynamic code execution" and the Obsidian team advised the Tasks plugin to disable by default after an RCE report. We decided v2 renders templates with LiquidJS (a pure AST interpreter, no eval anywhere) as the only documented default, and keeps Eta as a power-user tier behind an explicit **JavaScript Templates** opt-in: off by default, stored per device via `app.saveLocalStorage` (never synced, so a shared vault or synced `data.json` can never pre-enable it), consented through a one-time confirmation modal. The one toggle gates the entire dynamic-code surface — Eta template files *and* JavaScript frontmatter fields. Each Managed Frontmatter field declares its expression language explicitly (Liquid value-expressions via `evalValueSync` with types preserved, or JavaScript); the gate never reinterprets an expression, it only decides whether JavaScript fields run. While the gate is off, the plugin attempts no dynamic code compilation or execution anywhere: an operation that requires an inert artifact (an Eta template or a JavaScript frontmatter field) fails with an error naming it rather than falling back to substitute output, and even settings validation of JavaScript expressions waits for the gate.

## Context worth remembering

- The switch happened at v2 alpha deliberately: the v1→v2 migration was already breaking and no user had an investment in v2 Eta syntax yet. Post-2.0 this would have been a second breaking migration.
- Amended 2026-07-11 (pre-ship, in place): frontmatter was originally specified as gate-switched — one language for the whole field set, flipping with the toggle. Revised to per-field explicit `language` because the gate is per-device while the field settings sync, so gate-switching made one synced configuration mean different things on different devices. Existing fields are stamped JavaScript by a settings-data migration (old-default expressions translated to the Liquid defaults), and a gate-off device forbids authoring or validating JavaScript rather than warning about it.
- Amended 2026-07-12 (pre-ship, in place): inert artifacts were originally degrade-and-notify — an inert Eta template fell back to the embedded Liquid default and inert JavaScript fields were skipped, both surfaced via aggregated Notices. Revised to blocking typed errors (no implicit fallback): a note built from a template the user didn't choose, or written with part of its configured frontmatter missing, is silent policy substitution — worse than a refusal that names the artifact and the fix. Runtime-error isolation for throwing field expressions is unchanged; that's the author's own bug reported loudly per field, not policy substitution.
- Amended 2026-07-13 (pre-ship, in place): embedded defaults were originally shipped in Liquid only, with the Eta editions demoted to migration-doc reference material and the language dropdown creating an *empty* `.eta.md`. Revised to ship both editions for all six templates (the `filename` Eta edition recovered from its former `template.filename` setting default), because starting an Eta template from a blank file strands the user who chose Eta for a small tweak. Toward-Eta populates from the Eta default; reset follows the file's own edition (Eta reset writes the Eta default, gated on the JavaScript Templates flag); eject stays Liquid-only. The two editions are held byte-parity by the defaults test suite.
- Both engines bind template data to `zt` (Eta's `varName` is overridden from its default `it`), so `zt.…` is the single data vocabulary — the variable name is deliberately *not* a Liquid/Eta tell. The Data Explorer offers one `zt.…` copy-path regardless of the gate; there is no `it` alias, and a stray `it.foo` fails loudly. Path syntax (`.name`, `[i]`, `["special-key"]`) is valid in both engines, so one copied path pastes correctly into either.
- A LiquidJS prototype reproduced all v2 default templates output-equivalent: the `{% bq %}` block tag matches `bq()` byte-for-byte, `outputEscape` replicates the null/Temporal filter, `{% liquid %}` statement blocks handle logic-heavy sections with zero whitespace leakage, and LiquidJS invokes zero-arg function properties, so the link-helper data model (`{{ a.fileLink }}`) ships unchanged.
- Liquid truthiness (`""` and `0` are truthy) is the recurring footgun; the mitigation is normalizing empty strings to `null` when building `zt`.
- The template file extension names the language (`zotlit-<name>.liquid.md` / `.eta.md`); when both exist, Liquid wins and the Eta file is flagged as shadowed, so effective rendering never depends on the device-local flag. Includes resolve by template *name* through TemplateService, which dispatches per-name to the winning file/engine — mixed-language sets work, and include semantics live in the service rather than in eta codegen patching.
- The filename template moved from the `template.filename` setting string to a vault file for the same reason as the gate: a JS expression in `data.json` syncs, which would have bypassed the local-only consent.
- The scorecard flag does not disappear — static analysis keys on the presence of `new Function`, not on toggles. Disabled-by-default plus disclosure is the accepted posture per the Tasks precedent.

## Considered options

- **Handlebars / Nunjucks**: rejected — both compile templates through `Function` at runtime, so for vault-loaded user templates (precompilation impossible) they deliver zero eval-safety over Eta, while costing more helpers to express the same defaults.
- **Liquid-only, remove Eta**: rejected — burns the v1 power-user migration path and forecloses Templater-style customization; the ceiling would be re-litigated under pressure.
- **Sandboxing Eta (SES / ShadowRealm / wasm engine)**: deferred, not rejected — heavy machinery, easy to get subtly wrong, and the Obsidian team has signaled a possible official sandboxed-eval API. The gate leaves a seam: a future sandbox slots in behind the same toggle as a hardening upgrade without touching Liquid users.
