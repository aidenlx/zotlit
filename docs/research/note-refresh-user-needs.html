What "refresh without losing my writing" is really for

Every Zotero-to-Obsidian plugin hears the same request: update my note without destroying what I wrote. Under that one sentence are eleven separate jobs. Some are about content that comes from Zotero, some are about text the user wrote, and some are conditions on both. This page maps them, shows how each tool lays out a note, and says what the two decisions taken today already settle.

How to read this. Bars and ratings count independent voices across all sources, because reaction counts are tiny (the highest is 31). Each claim in the source file carries a label: handoff for the third-party findings report, prior crawl for the maintainer's 2026-10-04 Reddit and Discord crawl, and new for evidence collected today. The eleven jobs in one line each

J1 New annotations appear

"I wish I didn't have to rerun the command… and frequently forget"

ZI #216 (+11). Append-by-date breaks on clocks and sync, and drops new highlights in dated chunks. The live view removes this job from the update path.

J2 Zotero edits arrive

"The only way… is to delete everything and sync again"

Readwise #29. Copies spread to summary notes go stale too (ZotLit #294).

J3 Deletions leave the note

Rarely raised; users split between "remove" and "mark". In a copy, deletion collides with what the user wrote under it.

J4 Metadata changes arrive

"the integration with Zotero is static"

Citation #215 (+8). Titles, tags, citekeys: frontmatter that Bases and Dataview read, so it must be file text.

J5 Re-render after a template change

Wanted in bulk. Also the riskiest update: template mistakes corrupted user regions (ZotFlow #79, ZotLit #1274).

J6 A thought by one highlight

"manual comments and highlights exported together in their original context"

Bibnotes #104 (+3). No region boundary can protect a line inside a generated list. No one asked to type into a live view.

J7 Own sections and properties

"I use my front matter to organise my papers by subject"

ZI #475 (+4). Summaries, status, rating, subject. Obsidian strips YAML comments, so markers cannot live in frontmatter (ZI #317).

J8 Many notes at once

"a mess to roll back as I have 2000+ pdfs"

Bibnotes #11. Wanted: scope to existing notes, and a preview.

J9 Never lose work silently

"This is scary and I have lost one set of notes"

ZI #420. Readwise's append-only is the trust benchmark users cite.

J10 Auto or manual

"Automatic" is asked for J1 and J2; a quick manual command for J4, J5 and J8. It depends on the job, not the user.

J11 References to a highlight hold

"I don't want to loose those backlinks"

Forum 102028. Literal ask: a ^id. Real needs: follow back, see uses, survive updates. Decisions D1 and D2 serve these through the annotation URI.

Zotero child notes: does anyone need the implicit import?

Today the default template's ## Notes renders {{ note.noteLink }} for each child note. Rendering that link is the import: the first time a note is seen, a mirror file is created; after that the file is frozen; the only refresh is an explicit command that "Any local edits will be lost." No setting turns it off; the template is the switch.

Inference. About 25 voices want child-note content in Obsidian, and about 15 find copies stale, duplicated or unwanted. No voice on either side names ZotLit v2's implicit import, and no one asked for a file per child note without a command. Only ZotLit v2, among the tools sampled, does that. Explicit import keeps P3 and P4. A link or live list keeps discovery for P1 and P5 and cannot go stale. Nothing under S2 gives P1 "current and searchable" at once.

What the decisions above already settle

Stances S1–S3 (notes live in Obsidian; no full two-way sync; note taking stays out of Zotero) and decisions D1–D2 (no annotation ^ids; annotation URIs in the Citation Index) close several questions before any design work.

Settled

  • The region need not copy annotations: the live view meets J1–J3, and links meet J11 (a)–(c).
  • No stable ^ids to preserve through updates (D1).
  • "Where is this highlight used" and backlinks come from the index, not from text (D2).
  • No merge of user lines interleaved in generated content; no tool does it.
  • No two-way sync of child notes or annotations beyond the comment editor (S2); P6 is out of scope.
  • Thoughts about a highlight live in Obsidian (S1, S3): the user's own section with quote and URI, or the Zotero comment field.

Still open, with the user need behind it

  • Frontmatter ownership by key, without markers in YAML (J7, J4).
  • A safe update: preview for batches, fail closed, no-op when unchanged (J8, J9).
  • A home for J6 that users accept: they ask for append-only interleaving most.
  • Text where the user needs it: search, mobile, export, portability.
  • Whether the implicit child-note import stays, and what P1 gets instead.

Open questions

  1. How do users split between writing beside highlights (J6) and in separate sections (J7)? Nothing measures it.
  2. With annotations live, is the inserted quote enough for search, mobile and export, or do users want a "freeze to text"? The Query Block default is nine days old; no v2 user has reported yet.
  3. Does anyone link into the v2 managed region today, so that the D1 change breaks it? A vault-side count would answer this; user reports would not.
  4. Will annotation URIs written before D2, such as a callout's page link, be indexed like new ones?
  5. Do v2 users read, edit, or only follow the implicitly imported child-note files?
  6. Would P1 want a live, read-only rendering of a child note's body? There is no notes dataset today.
  7. Should region markers be visible syntax at all (ZI #157, ZotLit #1274, ZotFlow #34)?
  8. Do group collaborators want others' annotations in their live view, or only their own (ZI #352)?
