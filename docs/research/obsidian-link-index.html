Can Obsidian's index carry Durable Annotation Links?

2026-10-23 · Source observations from Obsidian 1.14.4 (extracted app.js and worker.js) and a runtime test in the fixture vault tests/fixture-vault-zotlit-v2. The companion text, with every file:line citation, is docs/research/obsidian-link-index.md.

ZotLit wants the Citation Index to know every zotero://open/…?annotation=… link in the vault, so it can answer "which notes use this annotation". This page shows where Obsidian's metadata pipeline loses those links, where ZotLit already sits in that pipeline, and what each indexing option costs. It makes no recommendation.

Short answer: no. The metadata worker turns a Markdown link or image into a cache entry only if its URL starts with ./ or ../, or has no : at all (worker.js:7770). Every zotero: URL fails that test, in every form and every place. It has done so since at least 0.12.19.

1 · Obsidian's parse pipeline

A vault change becomes a changed event in six steps. Parsing happens in a Web Worker. Hashing, caching, link resolution and events stay on the main thread.

Parsing runs in the worker, and so does the external-link filter. A plugin can read the output but cannot add a transformer. The transformer list is a module-local inside worker.js. A second instance of the same script renders reading-view sections (parseSections). Canvas parses text under 5,000 characters on the main thread with a copy of the parser and sends anything longer to the worker (app.js:177820).

2 · Where ZotLit's Citation Index sits

The Citation Index plugs into the end of that pipeline. It takes the changed event's text and scans it on the main thread. Wikilink citations it reads straight from the cache at query time. Resolving citekeys to Items happens in the ZoteroReads worker (ADR 0073). No ZotLit worker parses Markdown.

Orange is ZotLit. The Citation Index keeps its own IndexedDB store, ‹appId›-zotlit-citation-index, which mirrors Obsidian's ‹appId›-cache.

3 · Link-form coverage

Recorded means present in getFileCache() as links, embeds or frontmatterLinks. Results are from the runtime probe in Obsidian 1.14.4. The relative link ./Local.md is the control: it shows which places Obsidian reads at all.

The [] and ![] rows were not probed in every place one by one. They follow from the predicate: the link form does not change the result. A reference definition's URL survives verbatim, query string included, in referenceLinks. ZotLit does not write that form. Obsidian records links inside an inline %% comment; ZotLit's maskExclusions blanks them.

What a recorded link carries

{ position: { start: {line, col, offset}, end: {…} },   // zero-based
  link:     decodeURI(url), NFC, trimmed — "?" and "#" kept
  original: "[local](./Local%20Note.md)",               // exact source slice
  displayText: "local" }                                // "" for [](…)

4 · The four options

A · Reuse metadataCache

read links / embeds / frontmatterLinks
  • Not possible: no zotero: URL is ever stored
  • referenceLinks covers definitions only, a form ZotLit does not write
  • No API, public or internal, lists external links per file

B · Hybrid

cache events and structure + own link scan
  • Reuses changed text, parsed frontmatter, sections
  • Link extraction is still all ZotLit's
  • Two exclusion rules (%%) to reconcile
  • sections are root-level only

C · Own parsing, main thread

extend scan.ts beside citekeys
  • Same lifecycle as citekeys: events, backfill, store
  • parseAnnotationOpenUri ready; includes prefilter
  • Store schema bump → one full rescan
  • Cost scales with note size (about 12 ms at 1 M characters)

D · Own parsing, in a worker

ZoteroReads worker or a new one
  • Large notes and backfill leave the renderer alone
  • Bodies cross by message; no obsidian import in a worker
  • Generations, store ownership, async reads for views
  • Shared: competes with the ADR 0073 budgets. New: about 18 MiB heap

How expensive is the main thread?

A synthetic benchmark (Node 26, not Electron) measured a prototype annotation scan against today's citekey scan: maskExclusions, a zotero://open/ regex, then parseAnnotationOpenUri. Medians; bar length is log-scaled from 0.1 ms to 1,000 ms:

0.11 ms
10 k · citekey scan
0.32 ms
100 k · annotation scan
1.08 ms
100 k · citekey scan
13.1 ms

12.0 ms

991 ms

A note with no zotero://open/ link costs 0.016 ms even at 1 M characters, because the prefilter skips it. The citekey scan grows much faster than linearly on this dense input. That cost already exists today; this study did not diagnose it.
